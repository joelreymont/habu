Four cells BELOW DATA-START still differ between two builds of the same snapshot image, so each carries a live process address into every image. One is named: DATA offset 0x40 is DEF-WL-CELL (src/habu/layout.f:183), the definition wordlist scratch cell. It is written from CUR-CELL at the head of every definition (src/habu/habu2.f:2295 '14 DATA CUR-CELL LDR, 14 DATA DEF-WL-CELL STR,') and every reader is inside the definition path after that store, so zeroing it in the writer's scratch copy alongside the other SND-ZERO-LIVE cells is safe on the code as written - but it could not be PROVEN by running a restored image on the tree it was found on, because a restored image cannot compile a definition at all yet (dot habu-relocate-persisted-region-47de06b9). Add it to SND-ZERO-LIVE in src/habu/snap-lib.f as soon as that dot lands and a definition-compiling image exists to test it on. The other three are unnamed: DATA offsets 0x360, 0x3AA0 and 0x3EC0. 0x360 falls inside the locals-frame band that starts at LVF-OFF (0x2C0) and ends below LASTC-CELL (0x560); 0x3EC0 falls inside the protected-WID table PROT-WID-OFF (0x3CC0) to PROT-WID-END (0x40C0); 0x3AA0 falls in the run between SNAP-CELL (0x37F8) and TASK-TCB-CELL (0x3C88), which src/habu/layout.f gives no constant for at all. Naming them needs the band owner, not the nearest constant: read the writer of each band in src/habu/habu1.f and src/habu/habu2.f, or set a debugger watchpoint on data-base plus the offset during a snapshot build and turn the program counter into a name with SNAP-HEAP-OWNER:CODE-MAP (docs/debugging.md). Do not zero any of the three until its owner is named and its post-restore reader is accounted for; guessing is what this dot exists to avoid. Acceptance: each of the four is either reset by its named owner or recorded here with the reason it must stay, and the two-build compare reports zero differing cells below DATA-START.
