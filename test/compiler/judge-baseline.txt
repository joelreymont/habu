habu code generator judge
=========================

One row per corpus subject, judged on the bytes of machine code each habu
code generator emitted for the SAME program: the engine's emitter and the
native chain, which compile one text - the corpus source file itself, read
by tools/judge/src.f. A third generator, clang -O2 over a C twin of the same
program, is measured every run and PRINTED BELOW THE MARKER, because what a
host's toolchain emits is a fact about that host and no change to habu can
falsify one of its cells.

Regenerate this file with ONE command, from the repository root:

  bin/hb --load tools/judge.f > test/compiler/judge-baseline.txt

and check the tree against it with:

  bin/hb --load tools/judge.f -- --check

THE CHAIN COLUMN HOLDS EITHER BYTES OR A REFUSAL CODE, and which of the two
is what the verdict says. A refusal is measured every run by handing the
subject to the chain and recording what came back, so a subject that starts
being refused and one that stops both move this file. Nothing here is a list
of names anybody keeps in step by hand.

A ROW MARKED (tail) IS NOT LIKE FOR LIKE. The chain's routine there leaves by
a branch to a callee, so its byte count is the routine and not the whole of
the program: the callee is real and its bytes are under some other row or
under none. The callee is NOT added in, because one callee is reached by
several rows and adding it to each would claim its bytes several times over.
Read the gap on those rows as arithmetic rather than as a verdict.

A LARGER row is a finding and the check exits non-zero on it. A REFUSED row
is a raw measurement printed with its code: the capability it waits for is a
dot, and a check that failed on it would fail every day until that dot lands.
NO ROW IS REFUSED. The last one was PRESSURE-LOOP, whose -8508 was the
allocator declining to spill inside a loop; it closed by the loop no longer
holding the values, because src/compiler/native/loop.f moves reads that
cannot change with the turn out of the body. tools/judge-test.f asserts the
count at zero AND fails on a refusal carrying any other code, so a gap
cannot arrive unnamed and a row cannot go back unnoticed.

THE TABLE IS FINITE AND THE ORACLE BESIDE IT IS NOT. Every row here is a
program somebody wrote on an input somebody pinned, so what it can catch is
bounded by what anybody thought to write down. tools/judge/fuzz.f generates
straight-line integer programs from a CONSTANT seed, compiles each through
both code generators from one text, and requires the same cell back on the
ends of the signed range and on generated inputs. The gate runs a small
fixed number of them; the full sweep is a hand run:

  bin/hb --load tools/judge-fuzz.f

WHAT NEITHER THE ORACLE NOR THIS TABLE CAN SEE. Both columns of a two-way
row read ONE text. A reader that derived the wrong program hands the SAME
wrong program to both compilers, they agree about it, and no differential
test can notice - a shared-mode failure is the honest boundary of this
tool's coverage. What guards the shared half is the reader's own fixtures,
tools/judge/src-test.f, which attack it with sources built to fool it.

ds-old AND ds-new ARE THE CALLER'S OWN DATA STACK, touched. They count the
loads and stores each column's emitted code makes against the register the
running engine keeps its data-stack pointer in - all four spellings of one
access, over and under the pointer and in either register file. That is the
structural difference between the two code generators: the engine moves every
intermediate through a slot in memory and the chain holds it in a register
and touches the slot at the edges of the routine. It is EXACT, it moves for
one reason and it does not turn on host load, so it is compared here rather
than printed below with the costs. It is NOT the cost claim restated: a chain
that made the same accesses and took twice as long would pass every row of
it. That claim is bin/hb --load tools/judge-timed.f, run by hand.

ONE ROW TOUCHES IT MORE OFTEN THAN THE ENGINE DOES and the tally says so.
On CODEGEN-CORPUS4:CALL-FAN-BIG the engine CALLS its callee five times, so
the caller's own code touches no slot at all and the five callees do that
work inside their own routines; the chain copies the five bodies in and
makes one entry and one exit of its own. Neither number is the whole
program, which is the same caveat a (tail) row carries. A row heavier here
is a fact to read beside its bytes and its cost and not a verdict of its
own, which is why every number is pinned and none of them is a finding by
itself.

WHAT IS BELOW THE MARKER, AND WHY NONE OF IT IS CHECKED. Everything in the
table above is what habu's own chain determines, so it is the same number on
every host in every run and it is compared byte for byte. Two things are
not. A COST is a measurement, and a machine with every core busy - which is
what a gate is - moves one by more than any honest tolerance would catch.
The REFERENCE COLUMN is what another compiler made of another program on
this host, and today it is Mach-O only: a host that is not Mach-O has no
column at all. Neither can be falsified by a change to habu, so neither is
inside the compared bytes; both are printed under the marker as what they
are, with the spread this run actually measured beside the costs.

One call, in nanoseconds, with the measurement's own floor taken off. The
two habu columns are entered the same way - a quotation that calls one word
- so they lose the same constant and their difference is exact. The
reference column is reached through a foreign call, so it loses a floor of
its own: the row's own body run again against an empty C function of the
same arity, which marshals the same arguments into the same places.

MACHINE: linux-arm64. These numbers are local to one host and mean nothing
against numbers measured on another.

METHOD. Each body is generated from the row's ONE pinned input, certified by
the checker and compiled, then run 250000 times per timed run, 7 timed
runs, fastest run kept. The whole row list is measured 2 times over, so the columns
are interleaved rather than measured in blocks; each column keeps its
fastest.

EVERY PASS GENERATES ITS OWN BODY, so a row's two measurements sit at
different addresses with a cold instruction cache each time. That widens the
spread and it is deliberate: a placement a row was lucky in once is not a
property of the code the compiler emitted.

NOISE FLOOR, MEASURED THIS RUN: 644 permille. That is the widest gap between
two measurements of ONE program in this process, so a difference between two
columns smaller than it is not a difference. The floor itself measured 1995 ps.
