habu code generator comparison - the chain's own baseline
=========================================================

What this file is
-----------------
This is the recorded measurement of the NATIVE CHAIN - the code generator
being built - over the pinned word corpus in tools/codegen-compare-corpus3.f. It is the
second of the comparison's two references. The first is the clang column,
which says how far the chain is from a production optimising compiler and is
measured live because it is a fact about the host's toolchain. This one says
how far the chain has come from where it was, and it is committed, because a
baseline you are trying to beat has to be a thing that does not move.

The code these bytes describe is still the chain as it stood at the parity
campaign's baseline commit, 5dcb2867: no row's instructions have moved since.
The numbers themselves were re-pinned once, for the accounting change the
section above describes - the byte column began counting the trailing return,
which it had been leaving out while the reference column counted whole C
functions.

That re-pin is a checkable claim and not a date. Every row here gained
exactly four bytes across it, EXCEPT the six rows that leave by a branch and
so have no trailing return to have been missing - CODEGEN-CORPUS5:TAIL-BIG,
TAIL-WORK, TAIL-MID, TAIL-CHAIN, TAIL-PAIR and TAIL-AFTER - which gained
none. A re-pin that had touched code generation would have moved some row by
something other than four, or moved one of those six, and the run that
pinned these numbers would have said so.

Regenerate it, deliberately, with

    bin/hb --load tools/codegen-compare.f -- --update-chain corpus3

How a difference is read, and it is not the way the engine's table is read:

  bytes bigger   a REGRESSION against ourselves. It is a finding and the run
                 exits non-zero. We do not get bigger without saying so.
  bytes smaller  progress. It is NAMED and not counted, so that re-pinning
                 this file is a decision somebody takes after reading the
                 diff rather than something that happens quietly.
  cost           informational in both directions, under the tolerance the
                 engine's table states. A cost is a measurement.
  a row missing  the chain no longer compiles a word it used to. A finding.
  a row added    the chain compiles something new. Named, not counted.

Outputs are compared exactly in both tables: a row that answers something
else is not a smaller row, it is a wrong one.

How to read a row
-----------------
Every line that begins with the word old or new is a data row; every other
line is prose. A row carries, in order:

  path     which code generator produced the row
  word     the corpus word that was compiled, executed and timed
  bytes    how many bytes of machine code the word occupies - the WHOLE
           routine, the return it ends with included. The word's own
           dictionary record holds its code start address and a length,
           but that length is the span a CALLER may copy, which is
           everything before the trailing return, because copying the
           return would return from the caller. So the return is added
           back here. It is NOT added back for a routine that leaves by a
           branch, which has no trailing return to have left out, and
           which shape a record is gets read off the emitted code by
           tools/codegen-tail-probe.f rather than assumed.
  cost     how long one call takes, in thousandths of the cost of calling
           the empty word CODEGEN-CORPUS:NOOP in the same run. 1000 means
           an ordinary empty call; 4000 means four times that. Absolute
           nanoseconds are printed by the harness but not stored here,
           because they differ from machine to machine while this ratio
           largely does not.
  outputs  the values the word left on the stack when it ran on its pinned
           inputs, in the order the harness recorded them

The byte column was re-pinned once for an accounting change and not for a
code change. It used to be the recorded length alone, so every habu row was
four bytes short of the code that runs while the reference column's rows,
being whole C functions, were not: the two columns were not counting the
same thing, and CODEGEN-CORPUS:NOOP said so by reading zero bytes for a
word that is a return. The re-pin added four to every row EXCEPT the six
that leave by a branch and have no return to add - which is the check that
it was an accounting change: not one routine's instructions moved, and the
rows that did not move are exactly the rows the code says should not.
