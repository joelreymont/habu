Problem: every `:` definition's captured text is capped at BODYBUF-CAP = 8000 bytes: src/habu/definers.f DEF-CAPTURE refuses the token that would pass it (DEF-BODY-FULL, named since the earlier naming dot), and the buffer is BODYBUF-CAP+2 bytes boxed in the DATA header at BODYBUF-OFF = $800 (src/habu/layout.f, the header row near line 2563, src/habu/habu1.f EMIT-BCAP). Three more readers size themselves by the same constant: the checker's BODY-BUF (src/habu/verify-source.f line 97, E-VS-BODY-CAP throw at 557), the native compiler's TEXT-CAP span (src/compiler/native/compiler.f lines 75, 235, 240) and elaborate's RF-CAP span (src/compiler/native/elaborate.f lines 83, 91, 109). Two tests scale with it (test/outer-interpret.f rows near 573, 1572, 1633; test/runtime-regression-test.f 418-464). A fixed cap on a definition's text is a limit on checked input and stays a hack at any size (tim reraised it 2026-10-30; its origin was nine 900-byte string literals in a Tender definition). Ruling (carl): the text grows with the definition; no capacity constant survives. Acceptance: the DATA header holds the buffer's handle (base, length, capacity) instead of its bytes, the capture grows the owned allocation when a token would not fit, the checker's copy and the compiler's and elaborate's spans are sized by the definition's actual length from their owner's region, DEF-BODY-FULL, E-VS-BODY-CAP, TEXT-CAP and RF-CAP go, the two refusal rows become one row that loads and runs a definition larger than 8000 bytes, the runtime-regression fixtures no longer scale with a cap, the header row's length names the handle. A DATA-offset ABI change: build to convergence (two matching generations), the full suite, and the bootstrap mirrors (bootstrap/cg/*.fs) updated where they emit the header. Not a stage-1 incremental-build prerequisite: take it after habu-refuse-a-top-57851ac2 lands.
