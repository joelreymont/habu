Problem: src/compiler/native/x64ir.f (header), src/compiler/native/select-x64.f (header) and docs/x86-64.md ('The machine dialect') all state that a tie the allocator cannot satisfy is a copy the ALLOCATOR inserts, so the selector never inserts one. The allocator does not: src/compiler/native/regalloc.f MB-TIE1 (~1131-1152) treats a tie as a must-share union-find constraint and THROWS E-A64RA-TIE on a clash (the two ends cannot share a register); the clash path has never run because a64ir.f declares one tie (DEF-MOVK, whose ends are one live value). X64IR declares ties on every two-address form (add/sub/and/or/xor/imul, the *i forms, shli/shri, shl/shr, neg/not, cmpsel, selz - all result 0 tied to operand 0), so a real program clashes routinely: 'dup +' (both operands one value) and any operand still live after the op. Decision: the SELECTOR inserts the copy - a x64.mov of operand 0 into a fresh value immediately before the tied op, used as the op's operand 0, whenever that operand is also another operand of the same op or has a use after the op (liveness measured over the function the way LIT-FOLDED-AWAY? counts uses; a value whose last use is this op needs no copy); the allocator coalesces copies (MB-COPY?: BND-MOV symbol equality), so a copy that could have been avoided costs nothing after allocation. Acceptance: select-x64.f EMIT-BINARY / EMIT-BINARY-IMM / EMIT-SHIFT-IMM / EMIT-UNARY insert the copy under that rule; the three documents and INTEL.md's selection paragraph corrected to state it; test/compiler/x64-select.f: 'dup +' selects mov + add with the operation count asserted, 'x y +' with x read after the add selects the copy, 'x y -' with x dead after does not, a unary on a value live after copies; the arm64 engine byte-identical (nothing arm64 changes). Files: src/compiler/native/select-x64.f, test/compiler/x64-select.f, src/compiler/native/x64ir.f (header comment), docs/x86-64.md, INTEL.md. Verify: the suite; three generations with cmp; test/run.f.
