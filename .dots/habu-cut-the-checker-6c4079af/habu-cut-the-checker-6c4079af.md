Problem: checking a large generated source costs about 116k instructions per token, linear in size (tim, Maki lead, 2026-11-06; request /home/joel/Work/maki/.jj-ws.noindex/tim/.out/audit/rca-load/habu-request.md, report /home/joel/Work/maki/.jj-ws.noindex/tim/.out/audit/rca-load/report.md). Maki's STEP importer writes 17.6 MB, 43,992 colon definitions, about 1.36M tokens; `included` checks it in 16.1 s CPU (184e9 instructions, about 135k per token). Habu's sampling profiler on CHECK alone (13,235 samples): the type unifier 38% (R-RES 28.9% inclusive, R-COMPRESS 13.2%, RV-NEXT? 5.1% self, TV-ENSURE 4.5% self, 95% of it through RVT; src/core/checker.f :494, :1646, :1689-1705); LIN-TOTAL 15.6% inclusive, re-walking rows (:4387-4394); PROT-SPAN 10.7% self (about 12% with ! and c!) guarding the checker's own stores; symbol lookup 8.2%. Stack depth makes it worse: push N then drop N costs 96k, 82k, 137k and 384k instructions per token at N = 2, 8, 32, 128 (R-RES 62% and LIN-ROW-COUNT 40% at 128). By Joel's ruling of 2026-10-29, a build whose cost is out of proportion has a defect to root-cause first. Acceptance: the cause of each of the three costs (unifier, LIN-TOTAL rows, PROT-SPAN on checker stores) found from the reproducer and fixed, each in its own lane; the per-token cost on tim's design-8 and design-syn-128 measured before and after on one idle host. Reproducer: tim's entries design/design-{8,4,2,1,1f}.f and design/design-syn-{2,8,32,128}.f, run by Maki be33961b's build-project job.
