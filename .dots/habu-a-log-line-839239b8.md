Problem: src/lib/log.f:8-9 says a log call never throws for LOG's own failure and a line fd 2 refuses is lost. When fd 2 is a pipe whose reader has gone, LOG's write (log.f:148 ROW-OUT, log.f:156-160 OUT) raises SIGPIPE and the process dies with status 141 before the catch around the log call returns: case e4.f, rerun by the lead. FD:WRITE-FULL leaves signals to its caller (src/lib/fd.f:195-199), LOG takes no decision, and no layer of the runtime ignores SIGPIPE. A daemon whose stderr reader exits, or `hb … 2>&1 | head`, dies while reporting a failure. Source: the code review of package LOG Joel asked for on 2026-11-10 ("check that LOG:CODE+ is implemented correctly, and the whole LOG package"), report ~/Work/reviews/habu-10x-2026-11-10/log-review.md, cases ~/Work/reviews/habu-10x-2026-11-10/log-review/, run as `cd <installed Habu tree> && bin/hb --load <case>`. Lines are as of 92c8b01b. Acceptance: a line logged to a broken pipe on fd 2 is lost and the program goes on, as the header says; a test logs to a reader-less pipe on fd 2 and then runs its next statement. Design (the lead, 2026-11-10, after src/lib/aio-macos.f:191-209, which saves and restores the same flag around each host call): LOG owns it, for its own write only, under its lock. FD gains one public word, `FD:WITH-NOSIGPIPE ( fd [ -- ] -- )`, which runs the quotation with SIGPIPE held off on the descriptor and puts the descriptor's flag back afterwards, also when the quotation throws; ROW-OUT and NOTICE-OUT write inside it. The flag belongs to the open file description, which the parent and siblings share, so it is not left armed. On Linux the kernels emulate the flag by ignoring SIGPIPE for the process (src/habu/kernel-x64.f:1432-1444, src/habu/habu1.f:1020-1042) and there is nothing to put back; that split is the kernels' own.
