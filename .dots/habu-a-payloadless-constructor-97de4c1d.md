Wider than a payloadless constructor (installed hb, probes /tmp/plan-wctor, pr a 2-cell STRUCTURE):
- A constructor with a payload ignores the payload on the stack and takes its type from the declared output: `: VW ( pr -- n ) OPTION:SOME {: r:option<pr> :} 0 ;` refused at 'OPTION:SOME' "expected: a actual: pr"; likewise RESULT:OK (t-okwide.f), BOX:MAKE (t-boxmake.f), MATCH arms re-wrapping (t-match.f), IF/ELSE joins (t-joinA.f).
- OPTION:NONE has no payload; its type comes only from the declared output, so its use cannot settle it: `OPTION:NONE TAKE` with TAKE ( option<pr> -- n ) refused at 'TAKE' (t-call.f); `( -- option<one> option<pr> ) OPTION:NONE OPTION:NONE` refused, both read as option<pr> (t-two.f); `: VL1 ( -- option<n> ) OPTION:NONE {: r :} r ;` refused at ':}' (t-localn.f).
- A design (Plan, Opus) proposed checking such a definition twice: a first pass learns each constructor site's instance, a second checks with it, through CHECK-RETRY (src/core/checker.f:26681), which already re-checks a definition after an undefined name resolves. Asked which approach, Joel asked "what's the best approach for long term?" and pointed the item at the one-pass compiler; the approach is that work's to settle.
