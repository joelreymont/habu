Problem: C2c2 writes a colon definition's facts text only while no build space is open (BOOT:IMAGE-BASE-CELL 0), so a product record keeps entry bytes 32-39 at 0. Laying the text at `;` inside a build would put it in a file's DATA only when no earlier file of the build interned the same bytes (src/habu/intern.f:363-370 STRING through SPACE-STRING; src/habu/intern-table.f TEXT is FIND else LAY), so a file's object would depend on what loaded before it: test/fixtures/file-objects/pad.f (build B only, loaded first) defines MARK ( -- ) and FIRST ( -- n ), count.f defines BUMP ( -- ), HI ( -- ) and FILE-OBJECTS-LATE:ONE ( -- n ); build A's count.f object would hold `( -- ) ` and `( -- n ) ` and build B's would reference pad.f's (src/habu/linker.f DATA-REF+ :503-525), failing test/file-objects.f 'both builds wrote the object's bytes' (evidence /tmp/jerry-strings-objects.md, sent to carl 2026-11-07). Acceptance: inside a build each record's facts text travels by value in its file object's entries (linker.f RECORD+), never in the file's DATA; the link interns each text at one point after the file's DATA ends, the same in a cold and a warm build, so the product holds each text once and both builds write the same bytes; [32] holds the text's offset from the image base; test/file-objects.f passes with facts written in builds. Designed with carl's object format (habu-file-objects-l4-62887595). Files: src/habu/linker.f, src/core/check-hook.f, src/core/checker.f. Verify: test/file-objects.f; the cross-built hb reads a product word's [32]. Depends: C2c2 (habu-c2c2-store-a-34061842), carl's L4 (habu-file-objects-l4-62887595). Ownership: those files, coordinated with carl. Claim: unassigned.

From C2c2 (jerry, measured 2026-11-07 on qlkxxkuq): the old engine build (tools/native-build.f) never opens a build space, so it lays a facts text for each distinct effect of hb's own definitions, and the capture's 20-byte record rows (src/habu/aot-capture.f ACAP-COMPACT-ONE) carry no facts slot: the saved hb's records read 0 (bool>n, STR-LEN) while its DATA holds about 2,530 unreferenced texts, +154,904 bytes (/tmp/jrca.xM/scan.f: ' -- ' 2,576 times against 44 before). Acceptance case: a linked hb's records point at their facts texts and its DATA holds no facts text that no record points to.

E2 root cause and fix (carl, 2026-11-08, carl-c5a2 mlwnovlz "Keep a facts read past the signature cache drop", src/core/checker.f READ-LEAVE): test/file-objects.f failed E2 (warm program ≠ cold): the warm program also laid `( n -- ) parses creates creates-effect ( A | A -- A | A  ) ` as FOB-WRAP's facts text, where cold gives FOB-WRAP BOX's text `... creates-effect ( -- n ) `, interned once. In the warm build BOX is linked, so its facts are read when FOB-WRAP's body first binds it (READ-BOUND), and the read appends BOX's effect and created-effect records to the effect store above the mark FOB-WRAP's signature cache took (SIG-EFF-CACHE!). FOB-WRAP's wrapper rule kept the created effect's offset (WRAPC), then SIG-EFF-DROP rewound the store to the mark and the next record overwrote it (probe hb: at the read, record 42736 hasr 0 content 6856, store end 42800; at FOB-WRAP's facts text, the same record hasr 712 content 0, store end 42672). The record links rewind with it (RECORD-LINK-REWIND-EFFECT), so BOX itself is read again at its next bind; only the offset WRAPC held dangled. Fix: READ-LEAVE moves an armed cache's drop mark (RECEFF-UEND) to the store's end, so the drop stops above what the read added; the cache record stays, unnamed. Proof (/tmp/carl-hb.aM/hb): the E2 repro's warm program and map equal cold; both wrappers' texts read `creates-effect ( -- n )` warm; test/file-objects.f rc 0, `test: ok`, 3.2 s; census-M cold 240 compiled, warm 0, progM and map byte-equal.
