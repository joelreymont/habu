Problem: a build keeps nothing of a compiled file for the next build. L2 is split by section of the object (design .out/carl-file/design-fobj.md sections 2-3): L2a the key, the header and INPUT, written atomically; L2b RECORDS; L2c CODE; L2d DATA and STRINGS. Acceptance (L2a): tools/build-out.f moves to src/lib/build-out.f unchanged (a move; its nine requirers follow), so the linker can find the out root; LINKER's runner computes each file's key and, once the file's compile returns, writes <out>/obj/<hex key>.hfo atomically (FS:ATOMIC-WRITE-FILE) holding the header (magic HABUFOBJ, the 32-byte key, offset and length of the five sections INPUT FILES REQUESTS NAMES PIECES, 0 0 while empty) and INPUT (the size of the file's bytes and their SHA-256). The key is the SHA-256 of length-prefixed fields: ENGINE-ID:KEY$, the mode (engine or app), the target (arm64), the file's path under its root, the loader's key (empty for a file the build's body loads) and how many times that loader loaded the same path before; the load kind is left out (the runner does not see it, and the loader's key with the count already names each load). Files: tools/build-out.f to src/lib/build-out.f and its requirers, src/habu/linker.f, test/file-objects.f, test/fixtures/file-objects/build.f (new). Verify: test/file-objects.f runs two cold builds in two fresh hb processes (the boundary under test: objects are a function of the files, not of the process) with HABU_OUT in two temp dirs, and finds five objects in each, byte-identical by name and content, build A refusing test/fixtures/file-objects/residue.f with E-EVAL-RESIDUE and build B skipping it, and the program still prints Hi and ok; test/linker.f; test/compiler/arm64-link-run.f; full suite at landing (the move touches tools).
