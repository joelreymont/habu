Problem: src/lib/image-lifecycle.f:11-12 keeps the hook count N as a plain variable, which file objects carry, while HOOKS is a DYNAMIC-BUFFER whose #base/#ctl are scratch cells (src/core/layout-buffer.f DBUF-MARKS) that a link writes zero. The owners' registered flags are also plain and carried: build-out.f:32 CLEANUP-LIVE, engine-id.f:20 EID-CLEANUP-LIVE, task.f:454 SEM-CHUNKS-ARMED, task.f:1266 SWEEP-ARMED, context.f:504 HOOKED. A file that registers a process hook at load time would link a nonzero N against an empty HOOKS, and PREPARE would index past it (E-LAYOUT-BOUNDS), as ffi-abi.f's retired spans did (fixed in carl-c5a2 by moving them into 64-slot TYPED-BUFFERs). Harmless in hb's own build: N is 0 when it reaches end.f. Live in program builds (reproduces on the installed 7f950ea6 tree): three builds in one out root, a program whose top level logs a line, a no-require program, then the first again; the third throws 7122 (E-LAYOUT-BOUNDS) in app-end.f, rc 74, until another program's build rewrites app-end.f's object. Reproducer: `R=/tmp/x; mkdir -p $R/tmp; printf 'require src/lib/log.f\npackage LL\nLOG:WARN s" first" LOG:LINE s" built" LOG:TEXT+ LOG:;LINE\n;package\n: MAIN ( -- ) LOG:WARN s" main" LOG:LINE s" ran" LOG:TEXT+ LOG:;LINE ;\n' > $R/ll.f; printf 'TRUSTED: R ( -- ) recurse recurse ;\n: MAIN ( -- ) R ;\n' > $R/subject.f; export TMPDIR=$R/tmp HABU_OUT=$R/out; for p in ll subject ll; do bin/hb --load tools/hb-build.f -- $R/$p.f -o $R/p-$p </dev/null; done`. Observed: every program build under one out root shares one object for app-end.f; a program requiring log.f with no top-level log line, one taking its own TASK:FACILITY at top level and one requiring only string.f do not fail. Not shown: which word throws; inferred that ll.f links warm (N replays as 1, log.f:70 registers ROW-RELEASE at the first log line) while app-end.f recompiles and runs PREPARE against the empty HOOKS. In the suite, engine-stack-machine.f and aot-shifted-bytes.f build a no-require subject in the tree's out root, so test/file-objects.f's build L keeps its own out root (8 s cold per run against 1 s warm in the tree's) until this lands. Acceptance: every count and its table, and every flag and the registration it records, are both carried or both scratch; a warm build after an edit stays byte-equal to cold; the reproducer's third build exits 0; test/file-objects.f LOG-BUILD builds into the tree's out root and the suite stays green.
