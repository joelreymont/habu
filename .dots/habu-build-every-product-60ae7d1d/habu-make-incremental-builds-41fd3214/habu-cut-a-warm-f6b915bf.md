Problem: a warm build that links every file spends most of its time on fixed costs, not on linking. Warm census-G (67 of hb's startup files, all linked) takes 1.98 s; its profile (1 ms samples, 715) shows SHA-256 at 40% (ENGINE-ID:KEY$ hashes hb's 8 MB every build, 105 ms; HEADER-CK hashes the 6.3 MB of objects; source sums ~2.5 MB; Habu SHA-256 runs at ~77 MB/s), (PROT-SPAN) under ! at 12%, LE:U64@ at 20% (NFETCH-CHECK:RUN-ROW most). Objects are 6.35 MB for a 2.58 MB program (code 3.92 MB, data 1.19 MB, records 0.77 MB, stores+facts+acts 0.46 MB; checker-z.f alone 3.75 MB): code rows are 8-byte numbers, so a call site costs 40 bytes of rows. Detail: .jj-ws.noindex/carl-dots/.out/kept/c5a2/a2w/l6-notes.md "Night 4". DECISIONS build cost: rebuilds of Habu nearly instant. Acceptance: measure the full hb build warm once it links every file (the arm64-to-arm64 build); root-cause the largest cost by profile and remove it (no compression without Joel's approval: a compact row encoding is not compression). Files: src/habu/linker.f and what the profile names. Verify: warm wall and CPU time of the full hb build before and after, cold == warm bytes. Depends: the full hb build linking every file (S5c, C3).
