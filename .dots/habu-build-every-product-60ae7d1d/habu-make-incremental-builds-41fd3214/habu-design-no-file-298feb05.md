Problem: a file object carries the plain cells its file's top level stored, while the hook that cleans them or refuses the build (IMAGE-LIFECYCLE:REGISTER, run by PREPARE from app-end.f) exists only in the process that ran the top level. Shown: the hook count (c1efdd1a), the engine-path cache (a program printed the builder's bin/hb as its own path; c1c72c21), task.f's main park record (program dies -3606, rc 67), and a top-level TASK:NEW that a cold build refuses (rc 74, task at capture) while a warm build passes and its program dies signal 11. Per-owner scratch marks (DECISIONS 2026-11-09 'values a linked object replays') cover cleaning, not the refusal, and nothing checks a new owner. Joel 2026-11-10 on the hook-count fix: 'what is this fixing? is it fixing the cause or the symptoms?' Acceptance: a design, put to Joel one question per item the long-term rule cannot settle (a shared scratch declaration's name is one), under which no file object carries process state, a warm build refuses where a cold one does and a later owner cannot silently get it wrong; then its lanes filed as dots. Files: read-only. Verify: the design cites path:line for what exists and for the program path reaching each public item. Depends: none. Ownership: none. Claim: agent=jerry workspace=.jj-ws.noindex/jerry-owned (read-only design; brief .jj-ws.noindex/jerry-wasm/.out/briefs/design-process-state.md).

Review of c1c72c21 (2026-11-10), for the shared scratch declaration: EID-KEY (64), EID-MAPPED (1272) and EID-OPENED (176) in src/lib/engine-id.f are marked by sizes that are whole cells only by value; the one shared word refuses a byte count that is not a whole number of cells, so a mark cannot reach the next definition.

Review of "Set HOOKED after its registration" (2026-11-10): an owner that sets its registered flag after IMAGE-LIFECYCLE:REGISTER returns (the rule at PREPARE's comment; context.f HOOK-CAPTURE, task.f TASK-ARM-SWEEP) is left with the flag 1 and no hook if PREPARE runs the hook between the two on another thread; PREPARE runs hooks without the lock. No path in the tree does this (compiling on a task's thread exits 79). The design removes the flag-and-hook pair or says why the race cannot occur.

Measured (jerry, 2026-11-10, dot habu-measure-what-a-0b7f37f4, a prototype on 899110e0 that did not land): the reset in PIECE-END, after the STORED-N loop, zeroing every scratch row at or above OPEN-DP. Engine: three generations byte-equal before the signature, maps equal, a cold build by the last equals it. Cost, lowest of three: cold engine build 12.67 s to 13.19 s wall (about 4%), warm one-file edit 1.69 s to 1.73 s (about 2%); one engine build visits 3,307,833 rows over 496 pieces (the walk covers every row at every piece end) and zeroes 496 nonzero cells in 37 pieces. Suite: 269 of 270; the one red test is ffi-callback ("child stripped: exit 74"), cause IMAGE-LIFECYCLE's scratch count N (src/lib/image-lifecycle.f:13): TASK-ARM-SWEEP (src/lib/task.f:1393) registers a hook, the subject's require ends a piece and zeroes N, PREPARE (image-lifecycle.f:80) then runs no hook, so ROWS-SWEEP (task.f:1299) never clears the bound region. SWEEP-ARMED (task.f:1292) has the same shape. Both are owners this design changes (task.f's callback rows become scratch, image-lifecycle.f is deleted). Not measured: program builds outside the suite; what the other 495 zeroed cells are; growth with larger programs (pieces times rows). Result: the cost does not reopen "scratch storage lives apart" (DECISIONS.md, 2026-10-31 typed data); per-cell marks stay.

Joel 2026-11-10, asked to name the shared span-marking word: "i like scratch-bytes but why do you need to mark every cell? this smells! what problem are you solving? why not have the system understand that this is a buffer and that it needs to be scratch? are you solving the symptom or the fixing the cause?" Result (jerry): the shared word `( ptr u8 n -- )` is withdrawn; no owner lane that adds marks starts. A design for declaring storage scratch with the storage is in progress (brief .jj-ws.noindex/jerry-wasm/.out/briefs/design-scratch-declared.md); the owners convert once, to that form. The linker's file-end reset and live-task refusal (habu-end-a-file-5555197c) and the park fix do not depend on it.

Outcome (2026-11-10): designed and put to Joel; rulings in DECISIONS.md 2026-11-10 "scratch storage". Storage is declared scratch by the statement that allocates it (SCRATCH-ALLOT, SCRATCH-VARIABLE, SCRATCH-BUFFER:, his names); no shared marking word. Designs: .jj-ws.noindex/jerry-wasm/.out/process-state-design.md (file-end reset, live-task refusal, image-lifecycle.f deleted; its span-mark word and its widened scratch-cell-mark are withdrawn) and .jj-ws.noindex/jerry-wasm/.out/scratch-declared-design.md. Work: habu-add-scratch-allot-07fcc86b (the words, first), habu-move-every-scratch-4ca80ba0, habu-record-scratch-storage-4db7e41e, habu-end-a-file-5555197c, and the owner dots, which now wait for the words.
