Full context: the compile-shaped row of tools/codegen-workload.f cannot be moved by migrating a checker word, and the reason is measured rather than argued. One batch of 40 generated definitions costs about 27 ms in this workspace. SYM-FOLD-C, the fold the dot habu-reach-callers-already-054dd463 named, is entered 24389 times per batch (counted by migrating a fold that increments a created cell and moving the four call sites onto it), and 24389 calls of that word cost about 80 microseconds through EITHER code generator - 0.3 per cent of a batch - so making it infinitely fast cannot clear the row's own 3-4 per cent null-draw bar. Where the time goes: batch cost grows with the DICTIONARY. Measured, same source compiled at four sizes: ndict 11338 -> 25.9 ms, 12240 -> 26.8 ms, 13101 -> 28.1 ms, 13962 -> 29.4 ms, a slope of about 1.3 microseconds of batch per dictionary record, which over roughly 600 name lookups a batch is about 2 ns per record scanned and puts more than half a batch inside a linear name lookup. That lookup is the engine's own LFIND in src/habu/habu1.f - hand-written engine text, not a dictionary record - so no republication and no call-site redirection can reach it: xref.f's Habu lookup is not on the compile path at all (XREF-FOLD-C is entered ZERO times during a batch). Two ways out, and both are real work: make the engine's name lookup better than linear (a hash index over the record table, the way the checker's own symbol table already is), or measure the compile shape with a workload whose cost is not dominated by lookup. Until one lands, the compile-shaped row is a measurement of the engine's dictionary scan and should be read as one. AND THE ROW IS BIASED, not merely noisy: because a batch costs more the longer the dictionary is, EVERY consecutive pair of batch sequences has the second one slower, so all four null draws come out negative and so does the real row. Two runs after the checker's fold was migrated and its call sites moved: +1.6 per cent against a 5.1 per cent bar, and -2.5 per cent against a 1.9 per cent bar, the second printing REAL LOSS with nothing whatever having slowed down. A bar built as the largest magnitude of four draws does not remove a one-sided drift, and the row cannot be read until either the drift is removed from both arms or the lookup stops growing with the dictionary.
