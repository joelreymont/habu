Problem: BEARER's KEY (src/lib/net/bearer.f:332-336) makes one worker the fetcher of the JWK Set; LOOKUP (:318-321) hands every other worker that asks while FETCHING is true the answer CACHED (:322-324) gives from the set as it stands, and with no set yet that is UNAVAILABLE, which REFUSE (:400-403) sends as a bare 503. So on a fresh service, every request that arrives while the first key fetch is in flight is refused 503 though the issuer is up; for a set that lacks a new kid during a refetch, the same path answers INVALID, a 401. Found from Maki (tim, 2026-11-09): of three concurrent first list_projects calls on a fresh maki, one answered 200 and two 503 in 10 of 10 rounds; with the JWK Set served through a proxy that waits 2 s, requests 2 and 3 got 503 in about 45 ms while the fetch ran, the first 200 after 2.08 s, and a fourth after the fetch 200 (5 of 5 rounds). Sequential requests never fail. Reproduce: a maki configured with a test issuer whose key endpoint answers after 2 s, sent three requests 0.3 s apart. Maki does not need it now: MCP clients send initialize first, which fetches the set before concurrent calls. Acceptance: a request whose answer from the cached set is not ADMITTED while a fetch is in flight waits for that fetch and answers from the set it settled, bounded by the fetch's own limit, so a cold start answers every concurrent request 200 and 503 stays for an issuer that cannot be reached; a regression in BEARER's tests that holds the key endpoint open while several workers ask. Files: src/lib/net/bearer.f and its test. Verify: BEARER's test file. Depends: none. Ownership: src/lib/net/bearer.f. Claim: unassigned.
