Problem: a warm engine build, tools/native-build.f reusing the file objects an earlier build cached (HABU_OUT, default .out), makes a different engine from a cold build by the same host, and the engine a warm build makes compiles differently. Measured 2026-11-09 by tim (Maki) on master 9858d273, CDHash from codesign -dvvv since cmp fails on the per-signing CMS blob, each cold build with its own empty HABU_OUT: installed hb builds m1 cold = e16114d2; m1 builds m2 warm (57 files reused) = a0e2cb75; m2 builds m3 and m3c cold = 113436d4 both; m3 builds m4 warm (66 reused) = f96d92db and m4c cold = e16114d2. So the same host gives m4 != m4c, and the warm-built m2 builds 113436d4 where every cold-built engine builds e16114d2. The body-cap series (tim-series) showed the same: its warm g3 (57 reused) differs from cold g3c and is one 16384-byte page smaller. FILE-KEY (tools/native-definition-cache.f, the object key) hashes the roles, target profile, ambient tier/checker/borrow/dispatch state and the instance key, not the compiling engine; the cause is not traced. Acceptance: a warm build equals the same host's cold build by CDHash, and so does the engine it builds; or the old cache goes with habu-save-load-and-b4287e01, whose acceptance already requires a warm build to write the same program byte for byte, and this closes with that proof. Files: tools/native-definition-cache.f, tools/native-unit-*.f, tools/native-file-*.f. Verify: from one host, HABU_OUT=<fresh dir> hb --load tools/native-build.f -- <a>/hb twice into the same HABU_OUT (the second warm) and once into a fresh one; compare the three CDHashes. Depends: none. Ownership: the build cache (carl). Claim: unassigned.
