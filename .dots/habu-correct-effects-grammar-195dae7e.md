Full context: writing formal/Common/Effects.v against src/core/checker.f surfaced four places where docs/effects.md describes a system we do not ship. That document is what a language model reads to write signatures, so a wrong grammar there produces code that parses and means the wrong thing. Verified against bin/hb, not argued from source. (a) SERIOUS - the top-level return-clause syntax at docs/effects.md:13 does not exist. The document gives sig = stack '--' stack ( '|' stack '--' stack )?, and writes the >R/R> examples at :174-175 that way. The checker's real top-level shape is ( Din | Rin -- Dout | Rout ): PSIDE (checker.f:3053-3062) reads the bar inside each side and PSIG (checker.f:3064-3072) puts the -- between the two sides. Measured: TRUSTED: >RB ( R a | S -- R | S a ) with R>B ( R | S a -- R a | S ) plus a use site certifies, exit 0. The documented spelling TRUSTED: >RA ( R a -- R | S -- S a ) parses SILENTLY on its own, exit 0, because PSIG stops after Dout=R, Rout=S and leaves '-- S a' unconsumed - but a word using it fails, exit 70, 'habu: in use-a: at R>A'. Silent truncation into a different meaning is the worst failure shape for a specification. Note the document's shape IS correct for quotations, where PSTACK (checker.f:2986-3010) parses [ in -- out | rin -- rout ]; there are two conventions at two levels and the document gives the quotation one for both. (b) the conname list at docs/effects.md:16 admits only i64 u8 u32 cell bool char str addr, but CT-INIT (checker.f:1121-1153) also registers n, f, r, f32 and u16 - n is at checker.f:1124 - and the document's own prose and examples use n, so its grammar cannot parse the document it belongs to. (c) integer widening is mentioned only in passing inside the pointer section at :155-163; the real rule is INT-WIDENS? (checker.f:1192-1203) and UNIFY-WIDEN? (:1205-1207), applying only at UK-INPUT/UK-COERCE, with n subsuming any integer family both directions, and addr carrying its own sign class CS-ADDR (checker.f:1007,1133) so n flows into addr but u8 and u32 do not even at an input position. (d) DEFTYPE and DEFLINEAR are one grammar class at :18 and :64-73 claims a DEFTYPE nominal gets the same treatment as built-in roles, but DEFLINEAR goes through CHECKER-DEFLINEAR (checker.f:6296) to CT-ADD-LINEAR (:2766-2769), a global concrete-type row, while DEFTYPE goes through VNOM:MINT (lib/type/deftype.f:106-112) to CHECKER-DEFFAMILY, a package-scoped arity-0 family - different term tag, different unification arm, different scoping; lib/type/deftype.f:22 calls the table route the since-retired DEFTYPE, so the document describes the retired implementation, and its promised diagnostic at :70 is wrong too - a mismatch reports 'expected: n actual: serial<>'. Required result: docs/effects.md matches the checker. Fix the top-level grammar and distinguish it from the quotation form; complete the type list; specify the widening lattice including the addr sign class; separate DEFTYPE from DEFLINEAR. Acceptance: every grammar production and every example in the document is verified against bin/hb by loading it, not by inspection; the >R/R> examples certify as written. Each divergence is recorded as a comment at the matching definition in formal/Common/Effects.v.
