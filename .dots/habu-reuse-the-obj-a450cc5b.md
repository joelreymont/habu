Problem: a file whose top level does '<dir> SOURCE-ROOT:ROOT!' and then requires a file only that root reaches builds and runs, but is compiled again on every build: src/habu/linker.f CHECK-REQUEST resolves the request's spelled path under the root the check entered for the file, not the root current when the compile made the request, so the path differs from the one recorded and the object is BAD. ACTS-WALK, LINK-REQUEST and LINK-ACTS resolve the same way. Shown by test/aot-shifted-bytes.f ROOTED-REBUILD: the second build into one HABU_OUT prints the file's top-level line again; a control without ROOT! is reused. Zen and Tender set a root this way in files most of their trees require. Acceptance: each request and registry act is resolved, at check and at link, under the root current when the compile made it; an object is never reused when a new compile of its file would set another root; a file that never changes its root checks and links as before. Files: src/habu/linker.f, src/core/include.f, test/aot-shifted-bytes.f. Verify: test/aot-shifted-bytes.f ROOTED-REBUILD and its changed-file case, and a case for each of A and B below; test/file-objects.f. Depends: habu-keep-active-src-2da0b7b5 (same stack). Ownership: none. Claim: unassigned.

Parked 2026-11-10, needs a design first. A first attempt is the commit 'Reuse an object whose file set its root' at the bookmark kevin/reuse, not landed: the loader's event record carries the root current when a path was spelled (SOURCE-ROOT:EVENT-SPELLED@ answers it after the path), each REQUESTS and ACTS row of an object carries the file's load root and the row's root, both empty when they are equal, and the check and the link enter a row's root (ROOTS-HOLD?). It passes ROOTED-REBUILD, and its review found that it reuses a stale object: a row keeps only the canonical directory ROOT! arrived at, and the check confirms that directory still exists without redoing the ROOT! that named it. A: main.f does s" beside" SOURCE-ROOT:ROOT! and require helper.f, beside is a symlink to v1, and v1 and v2 each hold a helper.f; after 'ln -sfn v2 beside', with main.f unchanged, the next build links v1's helper where hb --load and a fresh build load v2's. B: a root computed from the environment (Tender's ZEN-ROOT:ROOT$ reads TENDER_KAIZEN_ROOT); switching between two checkouts that both exist links the first one's files, and the linker records no environment read (ENV-INPUT:OBSERVE has no observer anywhere). Master recompiles such a file on every build, so its program is right. Direction the review gave: record each ROOT! and each scope entry as a loader act with its argument as given and the root it was joined to, canonicalise it again at check and at link and require the recorded result (A); record in the object the environment reads a compile makes (B); both change the object format. Also from the review: ROOTS-HOLD? tests '<root>/.' within PATH-CAP, so a root of 1022 or 1023 bytes, which ROOT! accepts, never holds and its file recompiles on every build; test the root itself.
