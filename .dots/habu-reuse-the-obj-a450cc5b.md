Problem: a file whose top level does '<dir> SOURCE-ROOT:ROOT!' and then requires a file only that root reaches builds and runs, but is compiled again on every build: src/habu/linker.f CHECK-REQUEST resolves the request's spelled path under the root the check entered for the file, not the root current when the compile made the request, so the path differs from the one recorded and the object is BAD. ACTS-WALK, LINK-REQUEST and LINK-ACTS resolve the same way. Shown by test/aot-shifted-bytes.f ROOTED-REBUILD: the second build into one HABU_OUT prints the file's top-level line again; a control without ROOT! is reused. Zen and Tender set a root this way in files most of their trees require. Acceptance: each request and registry act is resolved, at check and at link, under the root current when the compile made it; an object is never reused when a new compile of its file would set another root; a file that never changes its root checks and links as before. Files: src/habu/linker.f, src/core/include.f, test/aot-shifted-bytes.f. Verify: test/aot-shifted-bytes.f ROOTED-REBUILD and its changed-file case, and a case for each of A and B below; test/file-objects.f. Depends: habu-keep-active-src-2da0b7b5 (same stack). Parked 2026-11-10, needs a design first. A first attempt is the commit 'Reuse an object whose file set its root' at the bookmark kevin/reuse, not landed: the loader's event record carries the root current when a path was spelled (SOURCE-ROOT:EVENT-SPELLED@ answers it after the path), each REQUESTS and ACTS row of an object carries the file's load root and the row's root, both empty when they are equal, and the check and the link enter a row's root (ROOTS-HOLD?). It passes ROOTED-REBUILD, and its review found that it reuses a stale object: a row keeps only the canonical directory ROOT! arrived at, and the check confirms that directory still exists without redoing the ROOT! that named it. A: main.f does s" beside" SOURCE-ROOT:ROOT! and require helper.f, beside is a symlink to v1, and v1 and v2 each hold a helper.f; after 'ln -sfn v2 beside', with main.f unchanged, the next build links v1's helper where hb --load and a fresh build load v2's. B: a root computed from the environment (Tender's ZEN-ROOT:ROOT$ reads TENDER_KAIZEN_ROOT); switching between two checkouts that both exist links the first one's files, and the linker records no environment read (ENV-INPUT:OBSERVE has no observer anywhere). Master recompiles such a file on every build, so its program is right. Direction the review gave: record each ROOT! and each scope entry as a loader act with its argument as given and the root it was joined to, canonicalise it again at check and at link and require the recorded result (A); record in the object the environment reads a compile makes (B); both change the object format. Also from the review: ROOTS-HOLD? tests '<root>/.' within PATH-CAP, so a root of 1022 or 1023 bytes, which ROOT! accepts, never holds and its file recompiles on every build; test the root itself.

Consumers: Tender's tenderd/zen.f:7 and src/office-source.f:3 set the root at top level, so both are compiled again on every build; nothing fails.

State 2026-11-11 (jerry): the Depends line names habu-keep-active-src-2da0b7b5, which no dot holds now (dot find finds nothing); ROOTED-REBUILD exists only on kevin/reuse (84d8ef9b), not on master.

Design (settled 2026-11-11 by the lead from Codex Astra's ~/.cache/tmp/design-root-reuse/astra/out.txt, cut): a part's object records the inputs its compile read and the check re-reads them; nothing is replayed. (1) Facts: while a part's own source runs, the loader records each root lookup (the joined absolute spelling and its canonical answer: ROOT! after its join against CURRENT$, WITH after its join against CWD$, every CWD$ read as '.' -> cwd) and each environment read (GETENV: name, bytes, absent apart from empty), each distinct fact once. A load's own root entry records nothing. (2) The recording belongs to the running loader, so a build's compiled copies of GETENV and ROOT! reach it: a new package SOURCE-FACTS in its own boot file ahead of src/os/env-base.f, its active recording reached through a new reserved header cell beside SRCLOC:SOURCE-CELL (cut from Astra's reuse of the loader record's change-count slot: that record is laid out in include.f, after env-base.f). (3) Object: each part's INPUT gains its entry root, its exit root and its facts; each ACTS row gains the root current when its path was spelled (the loader's events gain it as SOURCE-EVENT:CURRENT@; ROOT@ stays the resolving root); REQUESTS gains nothing, its request resolves under the exit root. Hard cutover. (4) Check: stamp, entry root equal to the current root, each root fact's canonical answer again (SOURCE-ROOT:ROOT?, one nonfatal lookup that ROOT! and WITH share, so a 1022/1023-byte root holds), each environment fact again; then acts and request resolve under their roots, entering a root only when it differs from the current one. Link: after the part links, the exit root becomes current (as ROOT! would leave it) before the request replays or the next part runs. (5) Deleted: linker ROOT-CK and FILE-ROOTS, SOURCE-ROOT:CHANGE-COUNT and its record slot, ENV-INPUT's observer (USE, RESET, OBSERVE), SOURCE-INPUT's observer (USE-OBSERVER, CLEAR-OBSERVED, OBSERVER-DEFAULT); none has a consumer. Public words, all called only by Habu packages: SOURCE-FACTS:RECORD ( [ -- ] -- ) and UNRECORDED ( [ -- ] -- ) (linker.f LOAD's compile turn around RUN-UNIT, :4763; NEST after it reads the part's facts, :4819), SOURCE-FACTS:FACTS$ ( -- ptr u8 n ) (NEST :4829, file end :4771), SOURCE-FACTS:ROOT+ and ENV+ ( ptr u8 n ptr u8 n -- ) (include.f ROOT! :645, WITH :593, CWD$ :273; env-base.f GETENV :78), SOURCE-ROOT:ROOT? ( ptr u8 n -- ptr u8 n bool ) (ROOT!, ROOT-CANON, linker PART-FRESH? :3896), SOURCE-EVENT:CURRENT@ ( n -- ptr u8 n ) (linker ACTS+ :2362); all reached from tools/hb-build.f:23 -> hb-build-lib.f:502 -> hb-build-core.f:357 -> APP-BODY :266. Cost: a changed environment value, root target or working directory recompiles the parts that read it, even when the program would come out the same. Lanes, one workspace, in order: A 'Record what a compile reads' (loader side: SOURCE-FACTS, GETENV, ROOT!/WITH/CWD$, ROOT?, CURRENT@, the two observers' removal); B 'Reuse the object of a file that set its root' (linker side and ROOT-CK's removal, with test/aot-shifted-bytes.f ROOTED-REBUILD from kevin/reuse plus cases A, B, a 1022-byte root and a changed helper, each built warm against a fresh build and hb --load); then the Tender measure (cold then warm server build, files compiled on the warm one) by the lead's census.
