Problem: in a cross-build (hb --load tools/hb-build.f -- X.f -o X) product text's include, require, included, required and provided run hb's own loader: src/habu/interpret.f LOADER? and HOST-WORD? (:127-145) route them to src/habu/linker.f RUN-FILE (:3293), which pushes hb's frame, while the product's SOURCE-ROOT words bind to the build's own copy of src/core/include.f, whose INCLUDE-DEPTH stays 0 and TOP null. So SOURCE-ROOT:ACTIVE-SOURCE throws 'include: depth underflow' (build rc 74), SOURCE-ROOT:WITH and CURRENT$ act on the copy's root while loads resolve through hb's, and ACTION$ and PARENT-ACTION$ stay unset. A program run, hb X.f, dies with the same underflow on master b94eaaef. Confirmed by an instrumented run: a print in the copy's required and PUSH never fired; a depth probe prints 0 at top level and nested in a build, 1 and 2 under hb --load. Witness: Zen's native server build (Zen workspace kevin-zbuild, change ylnnzqxs) stops rc 74 at its ACTIVE-SOURCE; Tender's tenderd/entry.f builds only because it calls CURRENT$ and WITH, never CHECK-ACTIVE. Probe trap: builds cache objects under ./.out, so a probe whose bytes are unchanged links and runs no top-level code; set HABU_OUT per run. Needs a feature design first (one frame for both loaders, or one loader; new public words likely): jerry's timestamps design (.jj-ws.noindex/jerry-inc/.out/design-timestamps.md rule 1) changes the same frame code, and carl (2026-11-09) keeps it out of the incremental-builds work. A drafted fix that mirrors hb's frame onto the copy from RUN-FILE (FRAME and ;FRAME words in include.f) was set aside: it keeps two frames in step instead of removing the split. Acceptance: a file calling SOURCE-ROOT:ACTIVE-SOURCE, CURRENT$ and WITH at top level and from a nested required file prints the same path, root and bytes under hb --load, through tools/hb-build.f and as hb X.f; Zen's native server build passes its source-root stage. Files: src/habu/interpret.f, src/habu/linker.f, src/core/include.f (as the design decides). Verify: a test/aot-shifted-bytes.f subject (HB-BUILD, GT-OUT$, GE-EXPECT-OUT-HAS, HABU_OUT inside the GT temp root), failing on master first. Depends: none. Ownership: unassigned. Claim: agent=kevin workspace=.jj-ws.noindex/kevin-loader

Design (2026-11-10, read at f34e9cdb): one loader record per process. (1) The top frame, the current root and the scope count become one record that each program's src/core/include.f allots and names in one header cell (SRCLOC:SOURCE-CELL, src/habu/layout.f, copied per task in src/lib/task.f) with ptr-cell!; all loader code reaches the record through data-base + that cell, so in a build the copy's ACTIVE-SOURCE, CURRENT$, WITH and NAMED? read and scope hb's record, and the copy's routed store gives the written program its own. INCLUDE-DEPTH goes (a second copy of "top is null"). (2) ACTION!, ACTION$, PARENT-ACTION$, their SOURCE-UNIT wrappers and the FR-ACT* frame fields are deleted: no caller. (3) hb X.f: main.f's plain route hands the loader the path (SOURCE-ROOT:RUN-PROGRAM), which opens a frame with the canonical path, its directory as root and the bytes it read, runs the text open (stack kept, CD legal) and pops; RUN-ROOT stays for stdin, the REPL and the --load row stream. (4) A target's copy refuses to load during a build, by name: when the process's record is not its own, its included, required, provided, WITH-BYTES and WITH-SUPPLIED die naming the path and saying to load at the file's top level (DECISIONS "choosing a file by target"). (5) A file sets its root with a top-level statement: CD-PATH becomes the public SOURCE-ROOT:ROOT!, legal inside a load or a WITH body, a scope's exit restoring the root it entered with; Zen (src/jobs/worker.f, src/document/pdf-text.f) and Tender (tenderd/zen.f, src/office-source.f) then set the root and require at top level. linker.f does not change; the frame's stamp fields are untouched. Rejected: letting words load during a build through an engine cell (a hook; reverses the 2026-11-07 decision), sharing all loader state, routing top-level SOURCE-ROOT: tokens to hb, the frame mirror, file-relative require. Lanes, one commit each, in order: the record behind the header cell with the test subject for --load and hb-build; the ACTION family's removal; RUN-PROGRAM with the hb X.f way of the subject; the refusal and ROOT!; then Zen's and Tender's files.
