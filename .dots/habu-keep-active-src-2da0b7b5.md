Problem: in a cross-build (hb --load tools/hb-build.f -- X.f -o X) product text's include, require, included, required and provided run hb's own loader: src/habu/interpret.f LOADER? and HOST-WORD? (:127-145) route them to src/habu/linker.f RUN-FILE (:3293), which pushes hb's frame, while the product's SOURCE-ROOT words bind to the build's own copy of src/core/include.f, whose INCLUDE-DEPTH stays 0 and TOP null. So SOURCE-ROOT:ACTIVE-SOURCE throws 'include: depth underflow' (build rc 74), SOURCE-ROOT:WITH and CURRENT$ act on the copy's root while loads resolve through hb's, and ACTION$ and PARENT-ACTION$ stay unset. A program run, hb X.f, dies with the same underflow on master b94eaaef. Confirmed by an instrumented run: a print in the copy's required and PUSH never fired; a depth probe prints 0 at top level and nested in a build, 1 and 2 under hb --load. Witness: Zen's native server build (Zen workspace kevin-zbuild, change ylnnzqxs) stops rc 74 at its ACTIVE-SOURCE; Tender's tenderd/entry.f builds only because it calls CURRENT$ and WITH, never CHECK-ACTIVE. Probe trap: builds cache objects under ./.out, so a probe whose bytes are unchanged links and runs no top-level code; set HABU_OUT per run. Needs a feature design first (one frame for both loaders, or one loader; new public words likely): jerry's timestamps design (.jj-ws.noindex/jerry-inc/.out/design-timestamps.md rule 1) changes the same frame code, and carl (2026-11-09) keeps it out of the incremental-builds work. A drafted fix that mirrors hb's frame onto the copy from RUN-FILE (FRAME and ;FRAME words in include.f) was set aside: it keeps two frames in step instead of removing the split. Acceptance: a file calling SOURCE-ROOT:ACTIVE-SOURCE, CURRENT$ and WITH at top level and from a nested required file prints the same path, root and bytes under hb --load, through tools/hb-build.f and as hb X.f; Zen's native server build passes its source-root stage. Files: src/habu/interpret.f, src/habu/linker.f, src/core/include.f (as the design decides).
