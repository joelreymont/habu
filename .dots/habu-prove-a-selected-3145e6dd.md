PARTLY DONE. tools/lint/schedule-lint.f now closes the phase half of the scheduling question and stops reading the selector: it loads test/run-lib.f and test/gate-stdlib-lib.f, walks every phase id, and (a) reds when a phase the runner has not retired appears in none of the schedule tables and is not named in TR-DEFERRED-ORDER, naming the registrations that phase's slice was the only runner for, and (b) judges a registration's label by RUNNING STDLIB-GATE:SLICE-SELECTS? - which is SUITE-RUN? with the label put through the suite registry's own store - for every slice a live phase asks for, instead of lexing `s" LABEL" SUITE-LABEL=` out of the source. Falsified both ways on 2026-08-07: deleting `$4` from TR-EARLY-HOST-ORDER reds with `phase 4  native stdlib tail slice: no order table in test/run-lib.f starts it and TR-DEFERRED-ORDER does not excuse it` followed by all 19 tail registrations by name; deleting the proof arms from PHASE-SLICE-TOKEN and STDLIB-SLICE? reds with the 8 proof registrations. Three phases that nothing started - $12 lint-artifacts, $13 lint-libs, $17 tool-lints, each an aggregate superseded by its own split groups - are now declared in TR-DEFERRED-ORDER rather than being silently absent.

WHAT IS STILL OPEN is the strict form of the label rule. A registration's label counts as covered when SOME live phase asks for the slice whose predicate selects it. That is weaker than the truth, because only a NON-RESIDENT phase spawns `test/gate-stdlib.f -- <slice>` and therefore only a non-resident phase runs the registration walk at all; a resident phase runs an inline GSI body and never consults a predicate. Today the non-resident stdlib phases are $4 tail, $28 proof, and the two deferred aggregates $12/$13 - so `tool`, `check-cli` and `lint-tools` are asked for only by resident phases, and every registration whose sole cover is one of those predicates is credited by a runner that does not exist.

MEASURED (2026-08-07, this tree): restricting the covering set to non-resident live phases leaves 7 registrations uncovered - shadow-lint, repl-lint, dot-dep-lint, maki-dep-lint, namespace-lint, error-code-lint, schedule-lint. They are not all the same shape and that is why this was not just switched on:
  - shadow-lint names tools/lint/shadow-lint-test.f, which is in NO gate fork list and genuinely does not run. The resident lint-tools body includes tools/lint/shadow-lint.f (the tool, which lints the tree) but never its fixtures.
  - repl-lint, dot-dep-lint, maki-dep-lint, namespace-lint and error-code-lint each name a CLI wrapper (tools/repl-lint.f and friends) that no list schedules, while the resident body runs the same lint through its core word with GSI-RUN. The work runs; the named file does not.
  - schedule-lint names tools/lint/schedule-lint.f, which is not in a list but IS loaded, because tools/lint/schedule-lint-test.f requires it and that file is in a list. The file-coverage rule only reads literal paths out of GSI lists and cannot see a transitive require.

SO THE WORK IS: decide each of the three shapes, then tighten. Probably schedule the missing fixture file (shadow-lint-test.f) for real; decide whether a registration may name a wrapper whose core the gate runs by another route, or whether those registrations should name what actually runs; and teach the file-coverage side to follow `require` from a scheduled file, or accept that a registration whose file is only reached transitively must say so. Only then switch LABEL-COVER? in tools/lint/schedule-lint.f from "some live phase asks for this slice" to "some live NON-RESIDENT phase asks for this slice" (TEST:PHASE-RESIDENT? is already public). Falsify by checking that the 7 above are green for a reason and that deleting $4 from TR-EARLY-HOST-ORDER then reds the 19 tail registrations directly, not only through the phase report.
