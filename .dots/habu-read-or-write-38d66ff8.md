Problem: macOS read, pread, write and pwrite answer -1 (EINVAL) to a count above INT_MAX (measured with a C probe: count 2147483647 on a 12-byte file answers 12, 2147483648 answers -1 errno 22). The read and write primitives (src/habu/prims.f:596, :729; arm64 BREAD and BWRITE in src/habu/habu1.f) pass the caller's count through, and library loops hand them the whole remaining length: src/lib/fs.f READ-FILL (:533) for FS:READ-ALL, and the write loops of src/lib/fd.f and FS:WRITE-ALL (not traced). Reproduced: FS:READ-ALL of a 2049 MiB file into a mapping one byte larger throws E-FS-IO (-2105) on the Habu installed 2026-11-11. ZIP:COMMIT of a replacement over INT_MAX bytes reaches the same write loop (src/lib/zip-raw.f EMIT-BYTES hands REPLACE-LEN to FD:WRITE-FULL, src/lib/fd.f SENT), read from the code and not reproduced. ZIP caps its own reads at INT_MAX (src/lib/zip.f PIECE-MAX, dot habu-read-a-stored-d13a61e4); Linux returns a short count instead (at most 0x7ffff000), so only macOS fails. Acceptance: FS:READ-ALL of a file over 2 GiB answers its size and FS:WRITE-ALL of a span over 2 GiB writes it, on macOS; every loop over read, write, pread or pwrite in src/lib that can be handed a caller-sized count asks for at most INT_MAX a call. Design: the cap belongs where Habu meets the host. The arm64 primitives live in habu1.f, which the one typed interpreter replaces (docs/design.md "Machinery being replaced"), so a cap inside the primitives is an acceptance case of that work; the library loops can cap today, and once the primitives cap, ZIP's PIECE-MAX stays only for its own pread binding. Files: src/lib/fs.f, src/lib/fd.f (list every call site first). Verify: the two reproducers above through bin/hb --load, and the fs and fd suites. Depends: none. Ownership: src/lib/fs.f, src/lib/fd.f. Claim: unassigned. Consumers: none meets this today as far as read: no file Zen, Tender or Maki reads or writes in one call is known to exceed 2 GiB (not measured).
