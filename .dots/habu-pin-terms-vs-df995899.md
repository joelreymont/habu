Problem: dot habu-export-the-checker-2bbc831c made the checker publish a row's width in CELLS (EFFECT-DIN-CELLS / EFFECT-DOUT-CELLS) precisely because a TERM is not a cell - one term of a W-cell layout family moves W cells. That distinction is implemented and the export is proved against the checker's own ER.MINI for every record (test/effect-read-api-test.f ERA-AGREEMENT, 1699 records, 0 disagreements). It is also known to MATTER in the tree: switching tools/chain-census-core.f's EFFECT wrapper from term counts to cell widths - the only change in that run - moved lib's declared-arity disagreements (E-NELAB-ARITY, the census handing NELAB:COLON an arity the body cannot match) from 28 to 19, so at least nine lib definitions carry a fixed row whose cell count differs from its term count. BUT none of them is reachable from a standing fixture today: a top-level probe over the whole loaded engine finds cells == terms for all 1699 certified records, because the differing definitions are PACKAGE-PRIVATE and only the census, which reopens each package, can query them. Every fixture in ERA-CELLS has cells == terms too, so the fixtures cannot tell a correct width from a term count. What DOES currently discriminate is mutation (recording width+2 instead of width+1 produced 550 ER.MINI disagreements and E-NELAB-CALL from the chain), which is evidence but not a standing test. Acceptance: a fixture declaring a layout family with instantiated width > 1, used in a certified signature, asserting EFFECT-DIN-N <> EFFECT-DIN-CELLS for the same row and that the chain compiles a call moving the CELL count - so a regression to term counts fails standing, not only under hand mutation. Files: test/effect-read-api-test.f (ERA-WIDTH package), possibly test/layout-buffer.f / test/extent-product-test.f for the declaration shape.
