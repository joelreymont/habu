Problem (aspen, Tender 2026-09-21, proposal ~/.cache/tender/verification/doc-timeout-lane/habu-low-speed.md, read-only): Tender's scraper has one whole-transfer limit, CURL:TIMEOUT! at 30 s; Georgia serves documents at about 50 KB/s (measured: 740,669 bytes in 13.5 s, 3,240,357 bytes in 58.8 s), so a document over roughly 1.5 MB fails with 'the transfer did not finish' although it never stalled, and the tender is lost. The right rule for a document is a stall test, not a ceiling: abort only when the transfer runs below a rate for a number of seconds. libcurl has it as CURLOPT_LOW_SPEED_LIMIT (bytes per second, CURLOPTTYPE_LONG + 19) and CURLOPT_LOW_SPEED_TIME (seconds, CURLOPTTYPE_LONG + 20); lib/net/curl.f binds neither. Acceptance: LOW-SPEED! ( handle n n -- status ) in package CURL beside TIMEOUT! - rate in bytes per second and a window in seconds, each checked with WITHIN-RANGE 0..MAX-TIMEOUT (a C long; 0 disables), each set through SET-NUM-RAW with the two option constants named like OPT-TIMEOUT-MS, the first option's failure status returned before the second is set; the word documented where TIMEOUT! is; tests in lib/net/curl-test.f: the suite's local server gains a dribble path that serves a body in timed chunks so the transfer is slow but never stalls, and (1) TIMEOUT! below the dribble's total time fails the fetch while LOW-SPEED! at a rate under the dribble rate with a one-second window finishes it with the whole body, (2) the existing /stall path fails under LOW-SPEED! alone with the same timed-out code TIMEOUT! yields, (3) a handle accepts the pair (EXPECT-OK) and an out-of-range value throws E-OPERAND (TTHROWSQ), all inside the suite's existing time budget. The addition is public surface: announce it to Tender (aspen) at landing. Files: lib/net/curl.f, lib/net/curl-test.f, the curl documentation page. Verify: the curl-http suite; test/run.f. Depends: none. Ownership: hazel (lib/net). Claim: agent=hazel workspace=.jj-ws/hazel-curl-lowspeed.
