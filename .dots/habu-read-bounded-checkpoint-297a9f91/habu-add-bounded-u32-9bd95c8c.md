Why: reading a weight value from a WSTORE slot today requires handing a raw span to a callback, and row-generalizing the callback combinators is unsound - a checked body can legally return the scoped pointer through the polymorphic result row (proven through the real checker against MEM:WITH-BYTES). The sound composition is value-level: the store answers bounded value queries and no span crosses any boundary. Exact result: public WSTORE:U32-LE@? ( WSTORE:store CAD-NUM:index CAD-NUM:byte-off -- WSTORE:store option<n> ) where the index is the typed slot ordinal and the offset is slot-relative. A bad slot index, an offset overflow, or a four-byte window crossing the slot or arm extent returns none without reading. Absolute-offset arithmetic is frozen: the slot-relative byte-off is validated as a CAD-NUM:byte-len distance, the stored row start is validated as CAD-NUM:byte-off, and the absolute offset comes from CAD-NUM:ADVANCE-BYTE-OFF with every numeric-result arm handled - CAD-NUM has no byte-off plus byte-off, and raw +, generic offset arithmetic, and new trust are forbidden. The mapped arm delegates that absolute offset to SAFET:U32-LE@?; the allocated arm advances with CAD-NUM:BYTE+ and reads exactly four little-endian c@ bytes. Uses WSTORE's existing audited projections only; adds no trust and no raw output; direct dependency on lib/adt/option.f is added explicitly. This leaf builds on the landed typed-slot prerequisite (CAD-NUM:index originates at GPT2TENSOR:SLOT) and owns the atomic WSTORE retype in the same commit that deletes WITH-SLOT: public WSTORE:SLOT! consumes CAD-NUM:index with every SLOT! caller migrated; SLOT-GUARD and ROW@/ROW! retype to CAD-NUM:index; NSLOTS@ validates as CAD-NUM:item-count bounded with CAD-NUM:INDEX-IN-COUNT?; the row address derives via CAD-NUM:INDEX-BYTE-OFF using ROW-CELLS cells as the byte width then CAD-NUM:BYTE+ from the row base; INIT-BLOCK refines each loop ordinal through CAD-NUM:INDEX; no INDEX>N and no trusted projection. A raw n SLOT! call becomes a checker rejection; a nonnegative index beyond the table count still throws E-SLOT.
