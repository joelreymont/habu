Problem: src/lib/f64-text.f PARSE is exact multi-limb arithmetic; on a text whose exponent is far from zero it is slower than the libc PARSE it replaced. Measured on macOS arm64, 600000 calls of one text per run, whole process: 2.2250738585072012e-308 takes 5.34 s against 0.63 s with libc; 6.644, -1.5e-7 and 123456789.125 take 0.46, 0.40 and 0.52 s against 0.54, 0.55 and 0.56 s, so short texts with a near exponent are not slower. The cause inside PARSE is not measured: the number for that text is about 36 limbs, and the shifts and the divisions by ten are suspected. Probe, installed hb on Linux arm64 from the tree: `require src/lib/f64-text.f : P1 ( ptr u8 n -- ) F64-TEXT:PARSE MATCH result ok OF drop ENDOF err OF drop ENDOF ;MATCH ; : RUN ( -- ) 600000 0 do s" 2.2250738585072012e-308" P1 loop ; RUN` takes 4.94 s, and 0.44 s with 6.644; the same loop over libc's strtod (`require src/lib/ffi-abi.f s" libc.so.6" FFI:SELECT-LIBRARY FUNCTION: STRTOD strtod ( ptr u8 n -- r ) ;FUNCTION`, the text ended by `\x00` in an `s\"` literal, `drop 0 STRTOD fdrop`) takes 0.17 s and 0.07 s. Acceptance: first measure where the time goes for that text (which words, how many limb operations); then PARSE on it costs no more than twice libc's time by the same measure, with answers still identical to libc on a listing of texts (the plist.f listing is lost). Files: src/lib/f64-text.f, src/lib/f64-text-test.f. Verify: the probe with each of the four texts before and after; bin/hb --load src/lib/f64-text-test.f; the libc comparison. Depends: habu-format-a-binary64-477e6a35 landed. Ownership: unassigned. Claim: unassigned. Consumers: Maki PARSE (10 calls), Tender PARSE (2); no consumer reported it.
