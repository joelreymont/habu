Full context: with the engine's name lookup made sublinear (dot habu-compile-shaped-cost-4e74a181), the compile-shaped batch of tools/codegen-workload-hot.f still costs 20.1 ms at ndict 11352 and 23.1 ms at 13976 - a slope of 1.13 microseconds of batch per dictionary record. That growth is now ENTIRELY the checker's: the same batch compiled with 0 set-check costs 723 us at ndict 11352 and 759 us at 13976, which is flat inside the noise, so the engine's own compile path no longer grows with the dictionary and everything that still does is Habu code in src/core/checker.f. The engine's sampling profiler names the words: over 20 batches at ndict 13000 the hot entries are SCAN-USIGS-SYM, USIG-MATCH-SYM?, USIG-SYM@, USIG-END?, USIG-NEXT and USIGS (the certified-signature store, walked record by record for a symbol), NORET-SCAN-SYM and NORETS (the no-return table), SUMV-FROM-CTOR-SYM and SUMV-CTOR-SYM@ (the sum-variant constructor table), and TFAM-FIND-PUBLIC/TFAM-FIND-IN (the type-family registry). Each is a scan of a table that grows with the number of certified definitions, and each runs per resolved call. The checker already owns a working hash index for its symbol NAMES (SYM-CAP/HIDX) and one for effect records (HIDX-EFF-SYNC), so the shape to copy is in the same file: key each of these tables by symbol id through an index sized from its own capacity, keep the linear scan as the fallback when the index is absent, and pin the answers against the scan before removing it. Measure with tools/dict-lookup-cost.f (four dictionary sizes, fastest of five) before and after; the checker-off row is the floor the checked row should approach. Depends: src/core/checker.f SCAN-USIGS-SYM, NORET-SCAN-SYM, SUMV-FROM-CTOR-SYM, TFAM-FIND-IN; tools/dict-lookup-cost.f; src/habu/prof.f (n prof-on / prof-report). AND THIS DOT IS WHAT THE WORKLOAD ROW IS WAITING FOR. tools/codegen-workload.f's compile-shaped row is biased rather than merely noisy, because a batch costs more the longer the dictionary is and so the second arm of every consecutive pair is slower. Run on 2026-08-04 with the engine lookup already fixed, all four null draws are still negative (-2.1, -1.7, -1.3, -3.2 per cent) and the real row printed -3.9 per cent against a 3.2 per cent bar - REAL LOSS with nothing having slowed down. The engine's half of the drift is gone; the row stays unreadable until the checker's half is too. Ownership: checker symbol-keyed tables. Claim: unassigned.
