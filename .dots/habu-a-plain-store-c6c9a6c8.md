Problem: a program's top-level 'NULL-PTR NCOMP-DISPATCH:DECL-A !' (src/habu/layout.f:899; TARGET-DECL-A :900 the same) changes the running hb, not the image, so a part that links on the warm build leaves it unchanged: probes ~/.cache/tmp/carl-aud1/decl4 and decl2 print 1 7 cold and 2 7 warm, rc 0 both. The same store with ptr-cell! goes to the image (habu2.f ROUTE-HEADER) and warm equals cold (probe decl3). The cause is not established: how a plain ! to a header cell is compiled in a build and why it is not routed; which header cells a program can name (SRCLOC:CURSOR, layout.f:496, is public too). Acceptance: the cause found with the probes; then either the store is routed or refused, or the cells stop being public. Files: src/habu/layout.f, src/habu/habu2.f, to be found. Verify: the probes warm equal to cold or refused. Depends: habu-re-enable-hb-a2404c26, habu-move-engine-internal-fc2ba551. Ownership: carl. Claim: unassigned. Found by the audit, carl-layout/.out/handoff-notes-22.md.

Cause (hunt, brief carl-layout/.out/briefs/plain-store-hunt.md; probes ~/.cache/tmp/carl-store/decl4 to decl7): a program's top-level code runs inside the hb that builds it, and DECL-A is that hb's own header cell $360 (src/core/pointer-storage.f:27 DATA-CELL, :74-75). A plain store is BSTORE (src/habu/habu1.f:2130-2131) at top level and PUT-PSTORE (src/compiler/native/emit.f:1553-1559) inside a word: the protected-band guard and the store, with no ROUTE-HEADER; only xt! and ptr-cell! route (src/habu/habu2.f:8268-8300). The image's cell never changes, so FIND-STORES (src/habu/linker.f:2051-2056, :2238-2242) saves nothing. c!, +!, the atomic stores, a store through CELL-VIEW (decl5, decl6: 1 7 cold, 2 7 warm) and a raw data-base offset store take the same path. Routing every plain store is wrong: the build hb's own header stores (src/core/layout-buffer.f:261, RECOVER-CELL at src/habu/definers.f:664 and :667) would land in the image. Not routing ! was chosen in the closed dot habu-route-header-stores-f38a1a0f.

Settled (lead, 2026-11-11): the defect is that a program can name the engine's own cells, not how the store is compiled. It is a case of DECISIONS.md "privacy" (:521-533: a word is restricted by a private section and the build strips private names; Joel, 2026-11-06, "can tweak sealing and stripping later"), so it waits for that work and gets no cell-by-cell patch. Acceptance replaces the one above: NCOMP-DISPATCH:DECL-A and TARGET-DECL-A (readers in checker-owner.f:18, interpret.f:244 and :253, outer.f:910-914, definers.f:722, :738, :840, :844 and :975, verify-source.f:1185 and :3001, packages.f:103-137, engine-origin.f:63 and :267, xref.f:489-491; stores only compiler.f:811-812), SRCLOC:CURSOR (layout.f:496) and the global CK-AOT-SIG-POOL-FIELD (checker.f:25202) are names a program is refused as undefined; probes decl4 to decl7 are refused. The raw data-base offset store is dot habu-checked-src-reads-4f721c9b. Not determined: whether clearing the build hb's DECL-A mid-build changes what it registers; whether built copies of checker.f's top-level code reach checker.f:29175 or :29513 in a program build; who stores the same offsets under other names ($2800, $2810, $2850, $2D68, $36A8, $800, STGT-INP-CELL, CK-TKA-OFF); whether TRANSFER-CHECKED (checker.f:29513) is reached by address.
