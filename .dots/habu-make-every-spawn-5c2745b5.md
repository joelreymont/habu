Problem: the process library writes the C strings posix_spawn reads with its own terminators and its own NUL checks instead of FFI:CSTR, the library's one NUL check (E-FFI-NUL) and terminator writer (src/lib/ffi-abi.f:586: "FFI is the only library code that writes a terminator"). PROCESS:ZCOPY (src/lib/process.f:203) copies the program path (process-command.f:370), the cwd (process-command.f:274, process-cwd.f:41), PROCESS:PATHZ (process.f:213), the pty device path (process-pty-io.f:147), PROC-ARGV+'s rows (process-argv.f:75) and the env rows (process-env.f:157) and appends a 0 without checking the bytes; CMD:ARG+ (process-command.f:214) appends an argument and a 0 the same way; PROC-ENV-CHECK-NAME and PROC-ENV-CHECK-ENTRY (process-env.f:136-148) refuse a NUL in a name but not in a value or entry. A NUL inside any of these cuts the string at the child: path '/bin/echo\0-x' runs /bin/echo rc 0, argument 'a\0b' reaches the child as 'a', entry 'HOME\0X=1' gives a malformed HOME row. Ruling relayed by tim 2026-10-30 (from Joel): one mechanism, FFI:CSTR. Acceptance: every C string the process library builds (program path, cwd, pty path, argv rows, env rows) is made by FFI:CSTR or FFI:CSTR! into its owner's buffer; PROCESS:ZCOPY, the hand-written terminators in CMD:ARG+, PROC-ARGV+ and the env row writers, and the per-writer NUL checks go (the env checks keep only their empty and '=' rules); a NUL in a path, cwd, argument, env name, value or entry refuses with E-FFI-NUL before any byte is written; tests in src/lib/process-command-test.f (NUL path, cwd, argument, env value, env entry) and process-argv-test.f (PROC-ARGV+) fail before and pass after; the ZCOPY length tests in process-test.f move to the FFI:CSTR refusals they become (E-SPAN-LENGTH, E-SPAN-CAPACITY). Depends: none. Claim: unassigned.
