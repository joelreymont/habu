Problem: with `: EVC ( -- ) s" 1 drop" evaluate-closed ;` and `TYPED-VARIABLE KV [ -- ]`, each of these is accepted and puts EVC (renders) into KV. A returned parameter, `: PASS ( [ -- ] -- [ -- ] ) ;` then `['] EVC PASS KV !`: a returned parameter is not judged kept (src/core/checker.f KEEP-INNER skips the top-level outputs). A RECURSE argument, `: R ( bool [ -- ] -- ) swap if drop false [: EVC ;] RECURSE else KV ! then ;`: the instance shares the block variable (OWNB-SHARE) but is judged before `KV !` raises it. More RECURSE shapes, each swallowing a token when run with `[: parse-name drop ;]` handed on: `: R ( n [ -- ] [ -- ] -- ) {: a p q :} a 0 > if a 1- [: parse-name drop ;] p RECURSE else q KV ! then ;` (an argument moved to another parameter), `: R ( n [ -- ] [ -- ] -- ) {: a p q :} a 2 = if 1 p p RECURSE else a 3 = if 2 [: parse-name drop ;] [: ;] RECURSE else q KV ! then then ;`, `: R ( n [ -- ] -- ) {: a q :} a 5 > if [: ;] else q then {: p :} a 0 > if a 1- [: parse-name drop ;] RECURSE else p KV ! then ;` (a join before the call), and RECURSE inside a quotation that is then executed, `[: parse-name drop ;] [: RECURSE ;] execute`. Judging at the call cannot hold them: whether a parameter is kept is known only at `;`, so the facts handed to each own parameter are judged there, against its block state, and the same program is judged alike whichever arm comes first. A loop back edge, `: W ( [ -- ] n -- ) 0 ?do dup KV ! drop [: EVC ;] loop drop ;`. An unsigned join, `: U dup KV ! [: EVC ;] SAME ;` with `: SAME ( a a -- ) 2drop ;`, then `['] EVC U`. The last two share a cause: a join writes into a term a keeping was already judged on (OWNQ-RESTORE covers only a signed word's publish). Acceptance: each is rejected at its keeping; the xt-effect suite passes. Depends: none. Claim: unassigned.
