Problem: test/http-accept-starved.f:186-187 (STARVED-ANSWER, macOS arm) failed once in the full suite at master 272c13b5's engine (gate g83, ~/.cache/tmp/jerry-gate/g83/suite.log: 'TFAIL assert 14 macOS resets the starved connection; expected 54 got 0'): the starved connection's read answered no bytes (assert 13 passed) with READ-ERRNO 0, so TCP4:READ answered closed (or failed with errno 0), not ECONNRESET. A second suite run at the same tip passed 274 of 274; the test alone passed 370 of 370 (30 serial, 40 eight-way, 300 two-way beside a suite run). Ruled out by C reproducers in ~/.cache/tmp/jerry-gate/starve: macOS closes a starved accept's connection with a FIN when no request is queued and answers the client's later data with an RST (peek.c), resets it when the request is queued first (starve.c), and resets it in 820 of 820 trials racing the request against the accept, with or without a flood of 170k closed-port RSTs (race2.c, race3.c, rlc.c, rlc2.c); net.inet.tcp.blackhole=2 does not apply to loopback (a refused loopback connect answers at once); tcp4.f and aio-macos.f read SO_ERROR only for AIO connects, which this test's blocking connect never uses. Open leads: the client's write status is dropped (GET's DROP-STATUS), so a write that met the reset first and cleared the socket's error is invisible; the suite's pool spawns the test with piped stdout and stderr (test/gate-pool.f GT-POOL-LAUNCH), the direct runs did not. Acceptance: the cause named with the evidence that shows it, and the test asserts what the OS guarantees, with its comment stating the fact. Files: test/http-accept-starved.f, src/lib/net/tcp4.f if the cause is there. Verify: the test under the pool's spawn conditions, repeated until the failure reproduces before the fix and not after.
