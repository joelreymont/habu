Joel-directed 2026-07-20, deciding the capacity architecture: 'why isn't capacity dynamic so that we can use a stack of any size?' The fixed-cap+named-die idiom is the right memory model for ENGINE-structural tables (dictionary, require registry, checker rows - bounded by the toolchain, not user input). It is the WRONG long-term model for INPUT-PROPORTIONAL structures - MIR node tables, backward tables, executor arena, capture-source buffer - where a constant means 'recompile the framework to build a bigger model'. Long-term design: two-pass model build. Pass 1 (capture) COUNTS - nodes, arena cells, source bytes are all derivable before allocation; pass 2 allocates the per-model tables EXACTLY sized as checked spans via the existing MEM-ALLOC machinery (lib/memory.f:54-62 - checker-integrated, already the idiom in the GPU tools), releasing them with the model. The named-die cap survives only as a sanity CEILING (absurd-input guard), never the working size. Real work items: (a) LAYOUT-BUFFER columns are today CREATE-time allotments sized by the constant (model-ir.f:139-148) - they need a span-backed variant whose base is bound at build time (pointer-stability audit: everything caching column bases must re-derive per model); (b) executor arena same; (c) capture buffer becomes streaming or counted-then-sized; (d) failure paths: allocation failure at build time is a NAMED error with nothing partially constructed (transactional, same bar as MIR-LN-CK); (e) snapshot/replay compatibility measured (per-model spans are runtime state - verify nothing persists raw column addresses).
