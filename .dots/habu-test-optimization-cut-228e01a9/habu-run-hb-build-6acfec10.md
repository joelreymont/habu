Problem: the documented command `bin/hb --load tools/hb-build.f -- ...` takes 9.08 s before it does any work, because tools/hb-build.f opens with `1 set-tier` and loads the tool inside EXECUTABLE-BUILD:WITH, compiling the whole library through the optimizer in a process that never captures an image (both makers are children). Measured 2026-09-30 on the d40cc36d engine: usage through tools/hb-build.f 9.08 s; the same with tools/hb-build-lib.f preloaded at tier 0 (the form the gate rows use) 0.44 s; engine boot 0.05 s. Decision: a saved image keyed through lib/build-cache.f was designed and prototyped and is not taken: it answers in 0.4-0.5 s per call against 0.44-0.66 s for the tier-0 load, because its own launcher costs 0.32 s to compute the key, and it costs a 13.6 s build on first use per cache root, per engine and per edit to any of 94 files, plus a sixth gate image family. It also saves nothing in the maker and app-build children, where the slow hb-build rows spend their time. Acceptance: the documented command loads at tier 0 with the same CLI, output and exit codes; the reason the tier-1 scope was added (37e78525) is found and shown not to be needed by the CLI process, or the lane stops and says what needs it; images built before and after are byte-identical; the per-call time is measured before and after; docs and the skill name one command. Files: tools/hb-build.f, tools/hb-build-core.f, tools/hb-build-lib.f, tools/hb-build-test-lib.f, test/stripped-image.f, docs/native-applications.md, skills/habu-build/SKILL.md. Verify: the hb-build suites that spawn the CLI; timing before and after. Depends: none. Ownership: the hb-build entry. Claim: agent=kestrel workspace=.jj-ws/r4-hbtier.
