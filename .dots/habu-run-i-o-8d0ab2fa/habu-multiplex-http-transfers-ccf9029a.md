Problem: every Tender transfer is CURL:PERFORM (libcurl easy, blocking) inside a pthread task, one thread parked in libcurl per transfer in flight; Joel: transfers are multiplexed by the kernel's asynchronous interface, not by threads blocked in calls (request with acceptance: ~/.cache/tender/verification/downloads-lane/habu-async-fetch.md), and, 2026-09-21, 'land the async primitives first, then build curl, etc. on top of those': this dot rides the AIO loop (habu-add-the-io-0c5a9630), not a loop of its own inside libcurl. Design (decided): package CURL gains a submit-and-park pair over libcurl's multi interface driven by one CURL loop task that waits through AIO. START ( handle ptr u8 len -- status ) claims a transfer record (MAX-TRANSFERS 64, E-CURL-CAPACITY when full), opens the memstream PERFORM uses, queues the record and writes one byte to the loop's wake pipe; AWAIT ( handle -- fetch-result ) parks the submitter with TASK:STOP until the record is done (the hint protocol of docs/threads.md: re-check after every STOP) and answers the stored result; CANCEL ( handle -- ) queues a removal, writes the wake byte, and the waiter is released with failed. The loop task: after every curl_multi_perform it reads curl_multi_fdset (read, write and exception sets; an fd >= FD_SETSIZE is E-CURL-CAPACITY for that transfer) and curl_multi_timeout, keeps one AIO:POLL-ADD ticket per fd in a GROUP (a ticket whose fd or interest left the set is CANCELled), one AIO:TIMEOUT ticket for the multi timeout (100 ms when libcurl answers -1) and one POLL-ADD on the wake pipe, then AIO:AWAIT-ANY; on any outcome it drains the wake pipe, adds or removes queued handles, calls curl_multi_perform, and takes CURLMSG_DONE messages from curl_multi_info_read (record found through CURLINFO_PRIVATE), takes the stream, copies the body into the submitter's span exactly as PERFORM does, stores the fetch-result, marks the record done and TASK:WAKEs the submitter. No CURLMOPT_SOCKETFUNCTION/TIMERFUNCTION: Habu hands libcurl no callback. Every per-handle option (URL!, METHOD!, HEADER+, BODY!, COOKIE-FILE!, COOKIE-JAR!, TIMEOUT!, LOW-SPEED!, FOLLOW!, scheme restriction) holds per transfer; a transfer's failure, timeout or stall ends that transfer only. A submitter HALTed while parked in AWAIT returns from STOP, CANCELs its own transfer and ends at its PAUSE. Acceptance (Tender's, lib/net/curl-test.f against the loopback fixture): thirty-two concurrent transfers complete with one CURL loop task plus the AIO loop and the process thread count (/proc/self/task) grows by those two alone; a stalled transfer ends by LOW-SPEED! or TIMEOUT! while the others complete and its fetch-result names the cause; a submitter released while awaiting (completion, CANCEL or HALT) leaves the loop running; for the same request the pair answers the fetch-result PERFORM answers (status, body, truncation); docs/curl.md describes the model.
