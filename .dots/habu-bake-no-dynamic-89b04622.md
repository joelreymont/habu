Problem: a DYNAMIC-BUFFER's control record is two DATA cells, the mapping pointer and the byte capacity (src/core/dynamic-storage.f), and the AOT capture copies the window's DATA; a build that reserved a buffer and kept compiling after NCOMP:CAPTURE-PREPARE released it bakes a non-zero capacity beside a pointer into a dead process, RESERVE's early return on need <= old then never replaces it, the generated reader's bounds check passes because the capacity is real, and the next generation dereferences the dead mapping: SIGSEGV inside @. Buffers whose need is module-sized escape by luck (a larger module forces a grow); a buffer whose need is near-constant always uses the dead pointer. Measured 2026-09-12 in .jj-ws/rowan-combine: the dropped opcode-map commit and commit ee18e60160aa 'Plan the combine once per definition' both die gen1 -> gen2 (rc 134) in tools/two-generation-build.f this way while the same engine passes every suite. Acceptance: every DYNAMIC-BUFFER declaration registers its control record in one core registry (a DATA-resident chain from a fixed head, built by the declaring form); the capture lifecycle releases and zeroes every registered record after the last thing that can compile, so an image carries no mapping and no capacity; boot verifies every registered record is zero and refuses by name otherwise (an image that carries a mapping is corrupt, not recoverable); the checker owns the effects of any new generated word (CHECKER-DEFDYNAMIC-BUFFER); regressions: an in-process check that after capture-prepare every record is zero, a forged image record refused at boot by name, and the chain reproduction: with commit ee18e60160aa rebased on the fix, tools/two-generation-build.f reaches gen 5 = gen 4 byte for byte; two same-host builds byte-identical; test/run.f red set unchanged.
