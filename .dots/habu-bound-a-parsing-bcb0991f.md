Problem: the source verifier keeps `parses:` rows only from files its scan reads (src/habu/verify-source.f PARSES-ROW :2932-2945; the load checks a row and keeps nothing, src/core/cell-effects.f:60). A file hb already contains is answered 'held' and not read (verify-source.f:3058-3059), so a row beside a word hb contains never reaches the row store: TOP-PARSER (:2979) finds no row (PRS-FIND 0) and stops the scan at the word (TOP-OPAQUE, :2995). Measured on master's hb: a program that requires src/lib/pg.f then defines a mistyped word ends `tools/check.f --verify-only` rc 0 with W-CHECK-DEFERRED at VERSIONED-LIBRARY (src/lib/pg.f:208) and the type error unreported. With `parses: LIBRARY 1` (src/lib/ffi-abi.f:1664), read only when the scan reads ffi-abi.f itself, the same was measured at LIBRARY for programs requiring src/lib/power.f (src/lib/power/macos.f:13) and src/lib/secret.f (src/lib/secret/macos.f:10). Direction (not designed): hb keeps the row with the word's binding, as it keeps `generates:` and `names:` (DECLARED-RENDER? verify-source.f:2853-2856, CHECKER-OWNER-ABI:BINDING-GENERATES), and TOP-PARSER and EXPORT-PARSES fall back to it. That changes what a checker record's facts text holds, a saved format: the design goes to Joel before a worker. Not determined: where the terminators of a `parses-through:` row are kept. Acceptance: with a built hb, verify-only of a program requiring src/lib/power.f, secret.f or pg.f and then defining `: BAD ( -- n ) s" y" ;` ends rc 70 with BAD's E-MISMATCH reported and one W-CHECK-DEFERRED per LIBRARY or VERSIONED-LIBRARY call; VERSIONED-LIBRARY gets its row. Depends: none. Claim: unassigned.
