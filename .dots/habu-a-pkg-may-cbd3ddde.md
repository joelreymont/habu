Problem: policy-admit admits a package whose public wordlist holds a word spelled `;`, on the installed Habu ee4b1361 and on the row-walk candidate (row-walk review, scratch program). The interpreter's keyword tables (src/habu/interpreter.f DEF-DESIGN-KEYWORDS, DEF-INTERPRET-KEYWORDS) and its own TOKEN-IS? lists (PACKAGE? :1287-1298, DEFINE? :2216-2227) are kept separately and nothing ties them together, which is also how seal-package was missed. Acceptance: POLICY-KEYWORD's answer is derived from the same lists the interpreter dispatches on, so a spelling the interpreter reads before lookup cannot be published; `;` is refused or shown harmless with a test. Files: src/habu/interpreter.f. Verify: refusal cases in src/lib/vocabulary-test.f for `;` and one spelling from each dispatch list. Depends: the row walk (habu-delete-the-jit-d9fdaf67) landing first. Ownership: src/habu/interpreter.f keyword tables. Claim: unassigned.

Joel, 2026-11-11, told that the row walk answered "is this name a keyword?" from rows of keyword spellings: "that's stupid, this should have walked the wordlist instead". The settled design says the same (docs/compilation.md "One reader": every construct is one immediate word in the dictionary; "there are no keyword lists"). What exists (jerry, read): POLICY-KEYWORD (src/habu/interpreter.f :1511) does walk the package's wordlist, but tests each name against six hand-kept strings (DEF-KEYWORDS, DEF-DESIGN-KEYWORDS, DEF-INTERPRET-KEYWORDS, DEF-NAME-ONLY-KEYWORDS, DEF-OP-KEYWORDS, DEF-P2-KEYWORDS, :1455-1477), because the interpreter reads its constructs by 98 `TOKEN-IS?` string compares and no wordlist holds them. So the acceptance above ("derived from the same lists the interpreter dispatches on") is replaced: the constructs are immediate words in a wordlist, the interpreter finds them by the lookup, and a package publishes a keyword exactly when a name in its public wordlist is found among them; the six strings, DEF-IN-TABLE? and its callers go. It is part of the one-reading design (dot habu-read-each-def-f7ce769a), not a table fix.
