Problem: checked source can overwrite the cells that hold the global, namespace and types wordlist ids: `data-base BOOT:GLOBAL-WL-CELL + !` succeeds on master. GLOBAL-WL-CELL ($7F0) and, by reading, TYPES-WL-CELL ($2D78) lie outside the protected bands that guard CUR-CELL ($28), WIDN-CELL ($30) and the PKG cells ($78-$90). With habu-a-load-accepts-db95cbfb's shortcut (src/habu/interpreter.f:1012 PKG-WID-SEALED? answers false for the build's global and types wordlists without a walk) a sealed package's wid stored into the cell lets a definition into the sealed package (a review's finding; its reproducer is lost). On the installed engine the store itself succeeds, at top level and in a colon definition, as a store of WIDN-CELL's own value into $30 does (both rc 0); after 'variable SW package S public get-current SW ! : A ( -- n ) 1 ; seal-package ;package SW @ data-base BOOT:GLOBAL-WL-CELL + !', ': S:EVIL ( -- n ) 5 ;' is refused 'E-SEALED-PACKAGE habu: <loc>: 'S:EVIL' is sealed', rc 84, and ': EVIL ( -- n ) 5 ;' is refused 'hb: no authenticated package context for this definition', rc 70. Settled by the long-term rule: the shortcut stays (without it every top-level definition of a build walks the dictionary) and the cells get the protection WIDN-CELL has. Source: Joel, 2026-11-10: "i want all issues identified to be dotted and fixed". Acceptance: a hunt names as path:line where the protected bands are defined and checked, and whether protecting these cells lies outside the machinery AGENTS.md says not to extend; then a store from checked source into each of the three cells is refused as a store into WIDN-CELL is, the reproducer is refused E-SEALED-PACKAGE or at the store, and test/seal.f holds a negative case per cell. Files: named by the hunt; test/seal.f. Verify: the reproducer under --load and as a build. Depends: none. Ownership: the engine's protected data. Claim: unassigned.

Hunt 2026-11-10 (bob): the protection is run time only, the DATA-BANDS table (src/habu/layout.f:1965-1981) read by the store guard (src/habu/habu1.f:298-337, src/habu/kernel-x64.f:304-345); no band row covers $7F0, $7F8 or $2D78. On master 204743ce no DATA-BANDS is left in src, tools or test, and those lines hold other code; src/habu/habu2.f:1405-1407 says a raw store to WIDN-CELL or the replay band exits 83 after the seal, and where that guard is now is not read. Three one-cell rows in layout.f would refuse checked source, but the linker stores into the same cells after the seal through a plain store (src/habu/linker.f MOVE-IN :5094-5096, RESTORE :5692-5694), so every build would exit 83; a writer for the linker is a new machine-code primitive in habu2.f and kernel-x64.f. Settled by AGENTS.md 'Machinery being replaced': not extended; this is an acceptance case of habu-build-every-product-60ae7d1d (a cross-build no longer swaps the running hb's wordlist cells, so the three band rows and the test/seal.f negatives then suffice).
