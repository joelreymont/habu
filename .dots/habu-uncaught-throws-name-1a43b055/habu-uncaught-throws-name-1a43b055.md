Problem: an uncaught throw prints `hb: uncaught throw code N` and nothing else: no name, no text, no place. arm64 prints it from assembly (src/habu/habu2.f:12609-12643, reached through UNCGH-CELL, src/habu/habu1.f:3759-3760, preset by src/habu/link-data.f:478); x86-64 calls the typed COMMAND-LINE:REPORT (src/habu/main.f:206-220, installed at main.f:282-285 and src/habu/link-x64.f:758-761); an x86-64 stripped program prints nothing. Neither reads the rows ERROR:CODE records. The loader catches and rethrows every throw of a loaded file (src/core/include.f:2002-2006), so the stack at the reporter is never the thrower's. Lines are as of 92c8b01b. Measured 2026-11-10 over the Claude Code transcripts of habu, maki, tender and zen since 2026-11-01: 850 uncaught-throw episodes, median 4 tool calls, 90th percentile 27, 1.64% of 453,140 calls; in 20 hand-checked episodes agents went looking for the code's name in 9 and the throw site in 7. A replay of Maki's eight refusals took 55 tool uses to locate five throws from today's output and 29 with one origin line. Design: the Plan agent's, 2026-11-10, ~/Work/reviews/habu-10x-2026-11-10/design.md parts A, B and D; asked whether Habu should also record each throw's file and line, Joel chose "Record places too (Recommended)". Acceptance: (1) One typed reporter, private in package ERROR (src/lib/error.f), stored in UNCGH-CELL by the linker for engines and stripped programs on every target; arm64's no-handler arm calls it with the code as src/habu/kernel-x64.f:1684 does, and the assembly reporter is deleted. Its first line on fd 2 keeps today's prefix and adds the name and text in LOG:CODE+'s order, the number alone for an undeclared code: `hb: uncaught throw code -30154 DRAWING:E-DRAW-PAPER: a view or annotation leaves the sheet`. Exit statuses 67, 70 and the silent 1..255 are unchanged. `0 throw` reports as an uncaught 109 with its sentence, exit 109; `die` with a code over 255 enters the reporter (src/habu/habu1.f:2052 BDIE), exit 67. (2) Where T0 compiles a call to the engine's throw (src/habu/t0.f:1140 DO-CALL, found by TERMINAL-CALL:BOUND?), it also compiles a place row (the file's path as the require registry holds it, relative to its root, and the line; the file alone for evaluated text that is not the file's own bytes) and a call to a private typed record word ( code place -- code ). The place row is data outside the word's bytes, so a line added to a body changes no other word's bytes (docs/architecture.md:208-211, a comment edit compiles one file). That word appends (code, place) to a per-task ring of the last 8 throws in the DATA header band; a ring row holds copies (path reference, line, values), never an address into a body (src/habu/habu1.f:1535). A require passes two compiled rethrows per include depth (src/core/include.f:1866 RUN-RANGE inside :1937 LOAD-CURRENT), which alternate, so a throw with the newest row's code and no other throw since keeps the run's first row and overwrites its second (a run is at most two rows), and the origin stays in the ring; a repeat at the same place overwrites the values. Each kernel's throw adds 1 to a per-task count and the record word notes the count its throw will get, so the reporter knows when the last throw had no recorded place; which kernel throws (divide by zero, a fault) add to the count is to be settled. Where T0 compiles `A B <cmp> if E-X throw then` (cmp one of <> < > >= = <= 0<> 0<; not 0=, a combined test or a predicate), it keeps the two operands for that arm and passes them, the code and the place row to a second private entry of the record word ( code left right place -- code ); the place row also holds the comparison and the ring row the two values. `throw` stays ( n -- ) and no source changes. (3) After the first line the reporter prints the ring, oldest first, one line each: `hb: threw -30154 DRAWING:E-DRAW-PAPER at src/drawing.f:364`, followed by `: <left> <op> <right>` for a compared throw (signed decimal, an unsigned value as `$` hex; left off when one operand is the thrown code and the other 0); when the last throw was not recorded, a final line `hb: the last throw's place was not recorded`. The lines state what the task threw, not a chain: an earlier throw that was caught and handled can appear above the failure's own, and docs/debugging.md says so. (4) Nothing is added to the replaced arm64 interpreter. A path tier 1 still compiles (the stripped-image driver, saved app images; Wasm modules compile through T0's src/habu/t0-wasm.f CALL) prints the name, the text and the not-recorded line until T0 compiles it. A path that does not throw pays no run time, and an image stays byte-equal between a cold and a warm build of one tree. Not in this dot: a public reader of the ring and any change to LOG:CODE+, since a lookup by code alone gives a daemon's later job an earlier job's place, so LOG:CODE+ keeps its 2026-11-06 wording; the callers between the thrower and the first catch; hints on an undefined word, which the closed habu-measure-what-an-5396ae6b bounds at 0.34% of calls.
