CRITICAL, destruction review of NCLOB. The soundness argument stated verbatim in src/compiler/native/clobber.f:14-27 and inline.f:29-36 — 'no two publications ever claim one slot' — is false: FORGET-DEFS-FROM (src/habu/xref.f:414-420) ends with XREF-FORGET-CP @ cp! and GENERATED-DECL-DICTIONARY:ROLLBACK (src/core/generated-declaration-dictionary.f:66-72) does r ROW.CP @ cp!, both rewinding the code pointer with no notice to NCLOB or NINL, whose rows are never dropped. A row keyed to address A then describes code that was reclaimed and rewritten. Three miscompiles reproduced end-to-end from checked Habu against shipped bin/hb (probes under /private/tmp/claude-501/nclob-probes/): p8.f caller answers 86 where 76 is correct (stale narrow clobber row under-saves, engine JIT writes x9/x10); pc.f 119 vs 110; pd1.f splices the WRONG BODY — a stale NINL row for old code at a reused address makes a caller of PD-B compute PD-A's answer (6 vs 26), arity-only cross-check passes. The validator reads the same row so nothing refuses. Fix must make row lifetime a consequence of code lifetime, not pointer monotonicity: strongest options are (a) register NCLOB and NINL as declaration-transaction participants and hook FORGET-DEFS-FROM so every row with entry >= cp is truncated whenever cp rewinds, or (c) key rows by (address, publication epoch) with the epoch in the call attribute beside KEY-ENTRY. Do NOT widen the default (it is already correct) and do not merely move checks around. Side effect to keep: closes the row leak where forget/re-migrate cycles permanently burn ROWS-MAX=128 rows (clobber.f:57,118-122) on recycled addresses. Regression tests must drive the REAL seam: migrate, forget, republish onto the same slot, assert the stale row is gone/refused and the caller saves the full set.
