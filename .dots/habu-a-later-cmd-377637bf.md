Problem (reported by tim from Maki's r2 font-lane review, 2026-11-03): CMD:ENV+ and CMD:ENV-ENTRY+ (src/lib/process-command.f:217-234) append every caller row, and PREPARE (:343-353) pushes each through ENV-ADDR+ (:297), so two ENV+ of one name give the child's envp both rows (MAKI_PROBE_X=first and MAKI_PROBE_X=second). What the child sees then depends on its lookup: a Habu child's GETENV takes the first (env-base.f CURRENT$ scans from the start), /bin/sh takes the last. Inherited rows already skip a name the caller set (INHERIT-Z :321-326, PROC-ENV-VEC-HAS-NAME?), and PROC-ENV-SET (process-env.f:261-268) replaces a name in place. Reproducer: /Users/joel/Work/maki/.jj-ws.noindex/tim/.out/r2/env-dup/env-probe2.f (loads child-getenv.f from /tmp/maki-r2-review-tmp/font/probes/), `hb --load env-probe2.f` from $HABU_ROOT prints both rows from /usr/bin/env and `first` from the Habu child. Ruling (carl, under Joel's relayed 'use your best judgement', 2026-11-01): a later caller row replaces an earlier row of the same name, as Go's exec.Cmd.Env (last duplicate wins), a Python env dict and PROC-ENV-SET do; no refusal, no new word. Acceptance: ENV-ADDR+ (or PREPARE) overwrites the envp slot already holding the name instead of pushing a second; the envp holds one row per name, the last value the caller gave, for ENV+ and ENV-ENTRY+ alike; a failing case first in the process-command tests through a real child (/usr/bin/env output has one MAKI-style row with the second value, and a Habu child's GETENV reads the second).
