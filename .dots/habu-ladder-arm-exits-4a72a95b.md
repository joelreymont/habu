Measured correction to the audit behind habu-collapse-branch-chains-63fbc39a. That leaf attributes ~28 gap bytes of CODEGEN-CORPUS4:LADDER-N to 'one mov;b join block per arm where clang falls through' and scopes them to two layout cleanups (retarget a branch whose target is a branch; place a single-predecessor join so its predecessor falls through). Neither cleanup can reach them. Measured on the real emitted code (tools/codegen-branch-inventory-run.f): LADDER-N is 168 bytes, holds 6 internal unconditional branches and ZERO chains - the branches all target instruction 40, whose instruction is not a branch, so there is nothing to retarget; and block 40 has SEVEN predecessors, so it is not a single-predecessor join and no placement can make more than one of them fall into it. The shape is: each arm is movz x1,<k> then b join, and the join is one mov (the result into the return register) followed by ret. What removes those branches is duplicating the one-instruction return block into each arm - the arm then ends movz; mov; ret, or movz; ret outright if the allocator gives the arm the return register directly, and the b disappears. That is return-block/tail duplication, a different transform from branch-chain collapse, and it is the only one of the two that pays here: duplicating a 1-instruction block plus its return replaces a 4-byte branch with a 4-byte return, which is a wash UNLESS the arm already writes the return register, so the allocator preference is part of the work rather than a separate nicety. Worth up to 6*4=24 bytes on this row. Check the same shape on CODEGEN-CORPUS4:BIG-CONSTS-N, MANY-LOCALS-N and FLOAT-MIX-N before building. Acceptance: LADDER-N byte count falls with answers bit-for-bit, no untouched corpus row moves, and a fixture pins that the arms end in a return rather than a branch. Depends: none. Ownership: the native chain's block layout / a new duplication pass. Claim: unassigned.
