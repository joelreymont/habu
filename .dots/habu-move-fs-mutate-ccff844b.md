Problem: src/habu/layout.f declares the FS-ABI band (fs.f's per-call slots, stat buffer, read probe and path copy) and the FS-MUT-ABI band (about 3 KiB: fs-mutate.f's second NUL-padded path, FS:MKTEMP-DIR-IN's name, FS:ATOMIC-WRITE-FILE's .tmp sibling) instead of TASK +USER rows. FS-ABI's comment (layout.f, the FS-ABI block) and the comment above BAND-AGREE in src/lib/fs.f give the reason: a require of src/lib/task.f from fs.f would load the task runtime into the build tool ahead of its target. That is false: tools/native-build-deps.f requires src/lib/codesign.f, which requires src/lib/fd.f, which requires task.f, so the build tool already loads task.f from source; fs-mutate.f also requires fd.f now. src/lib/CLAUDE.md: a module the engine does not bake takes rows from task.f. Each band costs a bootstrap step: an engine that predates it dies E-UNDEFINED (FS-ABI:STAT-BYTES, FS-MUT-ABI:PATHZ2-BYTES), rc 70. Acceptance: fs.f's and fs-mutate.f's buffers are TASK +USER rows; both bands, their E-FS-BAND checks (fs.f BAND-AGREE, fs-mutate.f:74-76), their CLAIM rows (src/habu/data-claims.f), their SND-ZERO-BAND rows (src/habu/snap-lib.f) and their adjacency asserts (src/lib/fs-mutate-test.f:1633-1636 and any in fs-test) are gone, and the neighbouring bands close the gap or the freed bytes are stated; no comment cites the task.f reason. First check that fs.f is not baked (not in src/habu/native-runtime.f's require closure); if it is, FS-ABI stays and only FS-MUT-ABI moves. Files: src/habu/layout.f, src/lib/fs.f, src/lib/fs-mutate.f, src/habu/data-claims.f, src/habu/snap-lib.f, src/lib/fs-mutate-test.f, src/lib/fs-test.f. Verify: engine build with tools/hb-build.f --engine, then fs-test, fs-mutate-test and fd-test on it; full suite (layout change). Depends: none (FD:SYNC landed in 3df0057e). Ownership: those files.
