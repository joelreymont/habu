Why: stale-status-lint was caught deriving a master-gate verdict from untracked files (see habu-migrate-trust-rows sibling dot on the same incident), which means the same tree can gate green in one workspace and red in another. Any other gate tool that enumerates files by walking the filesystem instead of consuming a tracked-tree list may hide the same defect. Behavior: audit every tool on the master gate list and every lint invoked by test/run.f lint-tools phases (filemap-lint, dot-dep-lint, stale-status-lint, enum-census, error-code-lint, namespace-lint, refine-lint, package/typed-local diff lints, and any others registered in the suite) for their file-enumeration mechanism; for each, either prove its walk roots contain only tracked paths by construction or add the explicit untracked-path skip with a hostile fixture. Record the per-tool verdict table in the dot on closure. Owner: tools/ lint family; no new package. Dependencies: the stale-status .blackboard exclusion dot lands first as the pattern example. Acceptance: a written per-tool table (tool, enumeration mechanism, tracked-only proof or added skip), and for every tool that needed a skip, a hostile fixture proving an untracked file cannot sway the gate through the real bin/hb --load path. Verify: the full master gate list green from both the main workspace and a fresh .jj-ws workspace on the same commit, byte-identical verdicts. Packaging prerequisite discovered 2026-07-26: six more lint cores are unpackaged (duplicate-definition, error-code, maki-dep, namespace, refine, repl), and the package ownership gate will reject any skip edit in them exactly as it did for stale-status; every core this audit must edit needs its own packaging dot first, copying the habu-pkg-stale-status-9d6a69b2 precedent and seam design.
