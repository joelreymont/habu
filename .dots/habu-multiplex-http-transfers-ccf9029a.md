Problem: every Tender transfer is CURL:PERFORM (libcurl easy, blocking) inside a pthread task, one thread parked in libcurl per transfer in flight; Joel: transfers are multiplexed by the kernel's readiness interface, not by threads blocked in calls (request with acceptance: ~/.cache/tender/verification/downloads-lane/habu-async-fetch.md). Design (decided): package CURL gains a submit-and-park pair over libcurl's multi interface driven by curl_multi_perform + curl_multi_poll/curl_multi_wakeup in ONE loop task (no CURLMOPT_SOCKETFUNCTION/TIMERFUNCTION: Habu cannot hand libcurl a callback into checked code, lib/net/curl.f ~120, so the socket_action/epoll shape is out of reach until foreign-to-checked callbacks exist, a compiler dot if ever wanted); START ( handle ptr u8 len -- status ) claims a transfer record, opens the memstream PERFORM uses, queues the record to the loop (lib/queue.f) and wakes it; the loop adds the easy handle, drives perform/poll, and on CURLMSG_DONE (record found through CURLINFO_PRIVATE) takes the stream, copies the body into the submitter's span exactly as PERFORM does, stores the fetch-result and signals the record's semaphore; AWAIT ( handle -- fetch-result ) parks on that semaphore and answers the stored result; CANCEL ( handle -- ) queues a removal and the waiter is released with failed; every per-handle option (URL!, METHOD!, HEADER+, BODY!, COOKIE-FILE!, COOKIE-JAR!, TIMEOUT!, LOW-SPEED!, FOLLOW!, scheme restriction) holds per transfer; a transfer's failure, timeout or stall ends that transfer only. Acceptance (Tender's, checked in lib/net/curl-test.f against the loopback fixture): thirty-two concurrent transfers complete with one I/O task and the process thread count (/proc/self/task) grows by the loop alone; a stalled transfer ends by LOW-SPEED! or TIMEOUT! while the others complete and its fetch-result names the cause; a submitter released while awaiting (completion or CANCEL) leaves the loop running; for the same request the pair answers the fetch-result PERFORM answers (status, body, truncation); docs/curl.md describes the model. Files: lib/net/curl.f, lib/net/curl-test.f, docs/curl.md, lib/errors.f. Slices: 1 bindings, records, loop task, START/AWAIT/CANCEL, one-transfer parity and cancel fixtures; 2 the concurrency, stall and release fixtures, docs, plus aspen's two points: a task HALTed while parked in AWAIT comes back (released with a failed result, or the CANCEL that frees it is named in docs/curl.md), and CANCEL from another task wakes a curl_multi_poll in progress (curl_multi_wakeup) so a stalled transfer is dropped promptly.
