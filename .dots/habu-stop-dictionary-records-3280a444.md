---
title: Stop dictionary records drifting between builds
status: open
priority: 3
issue-type: task
created-at: "2026-07-30T11:07:53.706864+02:00"
---

Two snapshot images built from one unchanged bin/hb still differ in 5,603 region bytes - 2,802 four-byte words, ALL of them inside the dictionary record area (region offset below DICT-SIZE). Measured 2026-07-30 after the address-literal relocation landed, which took the compiled-CODE area of the same diff from 310 differing words to 0, so this is the whole of the remaining region drift and it is a separate class. Three sub-classes, all identified from the record bytes: (1) field [0], the code start, of records ABOVE ndict - dead records left in the region by dictionary truncation, persisted verbatim, holding the writing run's absolute addresses; harmless to execution, but they make images non-reproducible; (2) field [24] of records whose name is INLINE - only the first N bytes are the name and the remaining bytes of the sixteen-byte field are uninitialised heap, which happens to hold stale addresses (e.g. the record for a two-character name carried 0x1017f5648 in one build and 0x103415648 in the other); (3) eleven LIVE records, indices 5608 to 5618 in the measured image (SNAP-TAIL-MARK, ARM64-W32I, MSK-MATCH?, XREG?SIG-TERM, M-NAME16-LEN, EMIT-DICT-PRIMS, TRL and neighbours), whose field [0] equals the region base plus exactly the region payload length or more - their code sits AT or ABOVE CP and is therefore not in the persisted payload at all, so EM-SNAPSHOT-REBASE-DICT's region band [DBASE, DBASE+payload) does not match them and they stay raw. Sub-class (3) is the one that can actually execute a wild address in a restored image; sub-classes (1) and (2) are reproducibility defects. Fix each at its cause, not by widening a relocation band: zero the inline-name field's unused bytes when a record is written; either truncate the record area or refuse to persist records above ndict; and for the live records above CP, find out why a live record survives with code outside the payload - either the truncation must take them with it or the payload must include their code. Do NOT make the region relocation bands wider to swallow addresses above CP: that would relocate a pointer to code the image does not carry. Acceptance: two consecutive snapshot builds from one unchanged bin/hb produce byte-identical region payloads, and a regression pins that.
