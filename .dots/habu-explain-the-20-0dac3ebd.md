Full context: measured by tools/codegen-workload.f, row scan-floor. Two byte-identical drivers (WORKLOAD:SCAN-OLD and WORKLOAD:SCAN-CTL-A, 324 bytes each, one call instruction each) calling two byte-identical 144-byte engine-compiled copies of the same body (HOT-ENGINE:FOLD-C and HOT-FIXED:FOLD-C, published seconds apart into different packages from ONE source string) differ by 18 to 35 per cent across every run, reproducibly, with the slower side always the one that reaches HOT-ENGINE. Fresh drivers compiled at the end of the run and interleaved reproduce it, so it is not driver layout and not measurement order: it tracks the CALLEE's publication. The workload's shape is one call per byte over a 4 KiB buffer, so the effect is per-call. Consequence: for that shape the code generator's own effect (SYM-FOLD-C is 1.26 ns of routine old against 0.81 ns new, per tools/codegen-compare.f) is an order of magnitude below the layout effect and the row reports NOT MEASURABLE. Work: find the mechanism with a tool - publish the same body at a controlled sequence of addresses and time a driver against each, so the report can say whether it is 64-byte line straddling, a fetch-window boundary, or branch-target aliasing - and decide whether the publication seam should align a routine's entry. That is a real code-quality question: an aligner would raise every hot leaf call in the system by the same 20 per cent. Acceptance: an alignment sweep in tools/, its numbers, and either a named mechanism or a measured refutation. Depends: tools/codegen-workload-scan.f (the call-site reader), src/compiler/native/publish.f (NPUB:NEXT-SLOT decides where a routine lands). Ownership: unassigned. Claim: unassigned.
