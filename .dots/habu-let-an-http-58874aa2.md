From tim (Maki), 2026-11-04. An HTTP/MCP handler never learns its client has gone, so a long call holds one of the HTTP workers until it ends on its own. Evidence at master 3378e2d6: src/lib/net/http-arena.f:38 MAX-WORKERS 8 (a protective server limit: stays); src/lib/net/mcp.f:722-724 NOTIFIED answers every 2025-11-25 notification 202 and drops it, notifications/cancelled included (the MCP spec says a server SHOULD stop the cancelled request); 2026-07-28 takes only requests, so closing the connection is a client's only cancel signal there, and nothing watches for it. src/lib/pg.f:1017-1036 READABLE-WITHIN/NOTIFY-WAIT watch only the PG socket. Maki case: its wait tool has no total bound (Maki DECISIONS 'Limits' 2026-11-04); a host times each call out (Codex tool_timeout_sec) and calls wait again, so each host timeout leaves a wait parked in AWAIT -> PG:NOTIFIED? until the job ends; after 8 the service answers nothing. Not reproduced end to end. Needs a design (a handler-side cancel signal the handler can wait on beside its own socket, or a cancel that unwinds the handler); new public words go to Joel.

Design: Fable Plan running from carl (2026-11-04); the result goes to Joel before any worker starts.
Design received (Fable Plan, 2026-11-04). Recommends: the listener watches each busy connection (AIO poll, readable with 0 bytes queued = client gone), halts the worker with TASK:HALT, joins it and re-activates it on the same slot; a pool pipe wakes the listener; per-slot WATCH state machine; no new public word; MCP notifications/cancelled stays ignored. Open facts being measured before it goes to Joel: whether Codex closes the connection at tool_timeout_sec, whether a non-main task can halt/join/re-activate a worker.
Codex close measurement blocked: the Codex account is out of usage until 2026-11-11 10:43 (or an account switch). Seen so far: Codex 0.166.0 asks protocolVersion 2025-06-18 and then speaks 2025-11-25 (the era that sends notifications/cancelled), no Mcp-Session-Id, initialize + initialized + tools/list on one keep-alive connection.
Restart measurement (master e49794ab, darwin arm64): a non-main task halts a worker parked in AIO:POLL, joins it and re-activates it on the same TCB, 1000 cycles x 4 runs (with and without nested finally cleanups), no errors, AT-EXIT ran once per halt, descriptors, RSS (35616 KB) and threads (3) unchanged, 77-131 us per cycle. Caveats for the lanes: ACTIVATE gives the worker the caller's dictionary snapshot and task region (I/O devices, APP-ENTRY, wids, DP bounds), so a listener-activated worker sees the listener's copy taken at START, not main's later state (task.f:1426-1460, :1561-1563); AT-EXIT hooks persist across runs and re-registering the same quotation is a no-op; ACTIVATE's state checks are not atomic (one activator per TCB). Untested: Linux io_uring, x86-64.
Joel 2026-11-05, asked to choose (after "aren't there standard unix facilities for doing this?" was answered: poll + FIONREAD to see the hang-up, a halt at the wait as pthread_cancel does, a self-pipe wake, Apache-style respawn): "your master rule is to do what's best for the long term, even if more work upfront. no shortcuts, hacks or workarounds. use that rule before asking me questions", then "so what's best for long term here?". Lead's pick: halt and replace, the design as written. Against a request-scoped cancel that keeps the worker (catch in both engines and TASK's lifecycle reworked, to save a ~0.1 ms restart and a hook re-run when a client gives up) and against every library wait also watching the client (PG, CURL and MODEL would learn about HTTP clients).
