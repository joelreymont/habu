Problem: a Habu pointer is a canonical zero-extended offset in an eight-byte cell; before narrowing, an access must prove 0 <= p <= 2^32-1, n >= 0 and p + n within the memory, in wide arithmetic, and the null reservation is enforced by pointer operations because address zero is in bounds (wasm-backend.md §6.1-§6.3, §17.5). HIR stages load, store, bload, bstore and mem (src/compiler/native/hir.f:51-99), and address literals carry DATA or CODE kinds (hir.f:557-560). Acceptance: WSEL lowers load, store, bload and bstore to i64 checks then i32.wrap_i64 and the access; a failed check records the fault kind and address in ctx and traps with unreachable, as a native fault is fatal; the check is high bits zero and p >= $10000 before i32.wrap_i64; the engine's bounds trap covers p + n; an address literal becomes the padded `i64.const` address site with its HIR kind (DATA to a linear-memory offset, CODE to an xt descriptor written by the linker); effectful loads, stores and calls keep their order (§16 Control and type invariants). Rows (structural, in test/wasm/select.f, SUITE wasm-select): an upper-bit pointer, a last-byte access and a null-region access each check the whole cell before i32.wrap_i64, a failed check stores the fault kind and address in ctx (offsets 32 and 40) and reaches unreachable, and each access is at offset 0, so p + n is left to the engine's bounds check. Running these rows (the last byte succeeds, one past the end traps in the engine) needs a linked module and a runner, so habu-build-the-first-66560106 runs them.
