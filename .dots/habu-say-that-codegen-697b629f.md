Full context: found while measuring dot habu-explain-the-20-0dac3ebd, written up in docs/codegen-placement.md. tools/codegen-compare-cases2.f times SYM-FOLD-C as "[: EXACTLY-A CODEGEN-CORPUS2:SYM-FOLD-C drop ;]" - the SAME constant byte on every iteration - so every branch in the body takes the same direction every time and never mispredicts. The same is true of the other branchy corpus words: WS? gets one fixed byte, TAG gets 9, MAX-DIM gets 3 7. The committed per-call figures for those rows are therefore perfect-prediction numbers and the tables do not say so. The size of the gap: codegen-compare reports 0.82 ns/call for the chains FOLD-C; the same routine on pseudo-random printable bytes costs 2.7 to 5.5 ns/call depending on where it landed (tools/codegen-align-sweep.f). A branchless 144-byte stand-in in the same driver costs 0.92 to 1.16 ns/call, which is the scale a perfectly predicted call to this body belongs at - so 0.82 is not wrong, it is a different measurement, and dot habu-explain-the-20-0dac3ebd spent a cross-tool disagreement chasing it. Work: either label the affected rows in the report as perfect-prediction, or give each branchy case a vector of inputs that exercises both directions per call the way the VECTOR arm already does for the answer check, and say in the tables which of the two a row is. Do not delete the constant-input row - a routines cost with predicted branches is a real and useful number; it just is not the only one. Acceptance: no row in the committed codegen-compare tables carries a per-call figure whose prediction regime is unstated, and a reader can tell a predicted-branch number from a data-driven one without reading the case file. Depends: tools/codegen-compare-cases2.f and the other cases files, tools/codegen-compare-report.f. Ownership: unassigned. Claim: unassigned.
