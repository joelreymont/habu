Hunt 2026-11-10 (/Users/joel/Work/reviews/habu-10x-2026-11-10/briefs8/reports/nullread-hunt.md): 22 accepted programs crash. Settled by the long-term rule, in this order: (1) a primitive that reaches memory is refused when its address operand is a known null (/Users/joel/Work/reviews/habu-10x-2026-11-10/briefs8/Refuse-memory-reach-through-null.md, in work; a first attempt inside BASE-BLOCK? and RAW-BLOCK? stopped, /Users/joel/Work/reviews/habu-10x-2026-11-10/briefs8/reports/nullread-fix-stop1.md: those see no operand); (2) NULL plus an offset gets a kind of its own; (3) BYTE-VIEW, CELL-VIEW and ptr-field keep the null kind. A null the checker cannot see (lost at a declared signature or a stored cell, 9 of the 22) needs a guard at run time; the fault handler is in habu2.f, machinery being replaced, so that is an acceptance case of habu-build-every-product-60ae7d1d. A null joined with data-base, and any base plus an unbounded offset, is the new dot on base plus offset.

Fix of step 1, 2026-11-10 (/Users/joel/Work/reviews/habu-10x-2026-11-10/briefs8/reports/nullread-fix2-stop.md, nullread-fix3-stop.md; posrortm, WIP): the memory flag set in PE-SPEC-ROW never reached a built engine's rows, which are read from facts text. Settled: READ-ROW takes it from the running engine's own primitive table (READ-MEMORY: PRIM-SPEC:FIND, REACH@ = R-MEMORY), no facts tag, no saved-format change. With it 'NULL-PTR c@', 'NULL-PTR count' and '5 NULL-PTR c!' are refused E-RAW-CELL-PTR at the token. 'NULL-PTR @' and '5 NULL-PTR !' still crash: @, !, atomic!, xt!, ptr-cell! and atomic-cas are intrinsics sent to CELL-FETCH-TOK, CELL-STORE-TOK and ATOMIC-CAS-TOK before any row is applied. Next: those three words refuse a known-null address with the same code and reason. The lost fixed-ABI and C2 flags have their own dot.
